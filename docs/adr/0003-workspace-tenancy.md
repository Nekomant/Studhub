# ADR-0003: Арендатор `workspace`, общие таблицы, изоляция в приложении

- Статус: принято
- Дата: 2026-11-11
- Отклоняется от черновика концепции (`teacher_id` на всех сущностях)

## Контекст

В MVP пользуется преподаватель-одиночка, на стадии 4 появятся онлайн-школы с ролями. Арендаторы маленькие (5–30 учеников), и их может быть тысячи.

## Решение

- Арендатор — `workspace`. Пользователи входят в него через `workspace_member` с ролью. В MVP у каждого один личный кабинет с ролью `owner`.
- `workspace_id` есть во всех таблицах арендатора, включая дочерние. `teacher_id` — только у урока и слота.
- Таблицы общие для всех арендаторов (не отдельная схема и не отдельная база на арендатора).
- Изоляция:
  1. кабинет указан в URL (`/api/v1/workspaces/{wid}/…`), middleware проверяет членство и формирует `ctx`;
  2. доступ к данным только через репозитории, принимающие `ctx`;
  3. составные внешние ключи `(workspace_id, x_id)`;
  4. тест «чужой кабинет → 404» на каждый эндпоинт.
- RLS в Postgres — не в MVP, можно добавить позже как страховку.

## Последствия

- Школа на стадии 4 — это кабинет с несколькими участниками, миграции ключа не нужны.
- Метрики и миграции общие для всех арендаторов.
- Крупного арендатора можно вынести в отдельную БД, скопировав строки с его `workspace_id`.
- Изоляция держится на дисциплине кода. Её страхуют составные внешние ключи и тесты.
