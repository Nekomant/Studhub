# ADR-0011: Фабрика-оркестратор

- Статус: принято
- Дата: 2026-11-16
- Меняет `docs/process.md`: §3, §4, §5, §6, §7, §7.1, §8.2, §9, §10; `docs/technical-design.md` §12; частично заменяет ADR-0010.

## Контекст

ADR-0010 сделал фабрику локальным скриптом без модели, но смешал роли: воркер сам проверял готовность задачи,
менял статусы и «разговаривал» с фабрикой текстовыми блоками (`СТОП`, `ЗАМЕЧАНИЯ`, `ГОТОВО`), а владелец отвечал
командами терминала (`answer`, `continue`, `drop`). Статусы In Progress и Review хранились в карточке, Done ставился
до выкладки в prod, а каждый шаг, который мог сделать скрипт, тратил токены модели. PR с документами и карточками
гонял весь CI, включая деплой.

Нужен процесс, где вся механика по схеме делает скрипт, а модель вызывается только там, где нужно суждение или
диалог с владельцем.

## Решение

1. **Фабрика — оркестратор-скрипт.** `pnpm factory` делает всю механику по схеме: выбор и проверку готовности
   задачи, ветку и worktree, права, проверки Definition of Done, push, PR, слияние, уборку, файл состояния.
   Команды: `factory ready`, `factory next`, `factory merge`, `factory status`.
2. **Корневая сессия (модель)** принимает команду владельца (`/ready SH-NNN`), запускает скрипт и по его результату
   одним вызовом `start_session` открывает подсессию с брифом. Дальше корневая сессия в процессе не участвует.
3. **Воркер — основной агент подсессии**, а не субагент. Он не проверяет готовность, не меняет статусы, не делает
   push/PR/слияние: пишет тесты и код по спецификации и сообщает фабрике сигнал («закончил», «остановился с вопросом»,
   «остановился из-за прав», число замечаний). Дальше решает фабрика: позвать владельца, запустить ревьюера, снова
   запустить воркера, создать PR, запушить, слить. `start_session` не задаёт агента и список разрешений, поэтому права
   задачи скрипт записывает в настройки worktree до старта подсессии.
4. **Ревьюер — отдельный процесс** (`dsh headless` с ролью `sh-reviewer`, модель `deepseek-v4-pro`, уровень `max`,
   только чтение). Ответ печатает в stdout: первая строка — вердикт («блокирует: N» или «чисто»), дальше записи трёх
   типов («блокирует», «замечание», «вопрос владельцу»). Скрипт проверяет формат, сохраняет замечания в файл, считает
   круги (не больше двух автоматических) и решает: вернуть воркеру или создать PR.
5. **Статусы.** В карточке остаются Backlog, Ready, Merged, Done. In Progress и Review не хранятся. Merged коммитится
   последним коммитом ветки и попадает в `main` вместе с кодом. Done проставляет шаг `deploy` после успешной выкладки:
   скрипт `scripts/mark-done.mjs` находит задачи в Merged, чьи squash-коммиты — предки выложенного SHA, и открывает
   лёгкий PR «Done: SH-…» с автослиянием.
6. **Модели ролей фиксированы.** Ревьюер — `deepseek-v4-pro` + `max`, верификатор тестов — `deepseek-flash`, критик
   спецификаций — `deepseek-v4-pro` + `high`. Модель воркера задаёт поле «Модель» в карточке (`pro`/`flash`, по
   умолчанию `pro`).
7. **Права воркера** — белый список: базовый набор плюс поле «Права» в карточке задачи. Запрещены push, `gh`, смена
   статусов и доступ вне worktree. Если прав не хватило, воркер не ищет обход, а останавливается.
8. **CI по изменённым файлам.** Лёгкий режим — все файлы в `docs/` (кроме `docs/process.md`) или в `backlog/`;
   в нём идут только `spec:check --changed`, проверка формата карточек и разбор документов `scripts/doc.mjs`, а
   пропущенные обязательные проверки закрываются job-заглушкой с тем же именем. Деплой на push в `main` запускается
   только при изменении файлов полного режима.
9. **Запасной вариант.** `pnpm factory run` с фоновым воркером (`dsh headless`) и командами `answer`/`continue`/`drop`
   остаётся на случай, если открытие подсессии или вызов агентов в ней не работают.

### Роли скрипта и модели

- `factory ready SH-NNN` — выбор задачи, Definition of Ready (`check-spec.mjs`), проверка актуальности по git
  (документы и файлы из поля «Затрагивает» не менялись после перехода в Ready, зависимости в Done), ветка и worktree,
  запись прав и модели воркера в настройки worktree, бриф для подсессии.
- `factory next` — одна команда, сама выбирает шаг по состоянию: проверки DoD скриптами (тесты, линт, типы, `ac:check`,
  красный коммит, правки тестов после него), проверяющий тестов `sh-verifier` только при правках тестов после красного
  коммита, ревьюер, счёт кругов, push, `gh pr create`, ожидание CI. Первая строка вывода — действие для воркера,
  вторая — фраза этапа.
- `factory merge` — после добра владельца коммитит статус Merged, пушит, ждёт CI, сливает squash, удаляет ветку и
  worktree, подтягивает `main`; перед слиянием запускает `sh-retro` и коммитит запись в `docs/process-retro.md`.
- `factory status` — текущий этап из файла состояния.

### Техдолг и ретро

- Неисправленные замечания живут в одном файле `docs/tech-debt.md`; `pnpm remarks` читает его.
- Ретро-анализ процесса делает `sh-retro` (`deepseek-flash`, только чтение) в `factory merge`; запись идёт в
  `docs/process-retro.md`.

## Рассмотренные варианты

- **Оставить статусы In Progress и Review.** Они не дают информации, которой нет в git и GitHub, и требуют лишних
  коммитов в карточку. Отклонено.
- **Ревьюер как субагент сессии.** Отдельный процесс на `deepseek-v4-pro` + `max` изолирует сильную модель от
  воркера и упрощает разбор вердикта скриптом. Оставлено.
- **Done ставить до выкладки.** Статус не отражал бы реальность: задача не готова, пока код не в prod. Отклонено;
  Done ставит шаг `deploy`.

## Последствия

- Заменяет `pnpm close-task`: уборку после слияния делает `factory merge`, Done ставит `mark-done`.
- Воркер больше не проверяет статус и Definition of Ready и не меняет статусы; эти проверки в `factory ready`.
- Жёсткие правила кода вынесены в скилл `sh-code-rules`, который подключают воркер и ревьюер; из `CLAUDE.md` правила
  удалены, остаётся ссылка.
- Проверяющий тестов `sh-verifier` запускается только при правках тестов после красного коммита, а не перед каждым PR.
