# ADR-0009: Отдельная админка платформы, сотрудники в `platform_staff`, маскировка ПДн

- Статус: принято
- Дата: 2026-11-12 (решения согласованы с владельцем 2026-11-11)
- Меняет ТД: раздел «Администратор платформы» в §6.2, §9 и флаг `user.is_platform_admin` в §4.2

## Контекст

В первой версии ТД админка была страницей `/admin/metrics` внутри SPA преподавателя. Доступ давал флаг `is_platform_admin`, а сессия была обычной, на 90 дней. Эта схема подходила для одного основателя и одного экрана метрик. Но админка понадобится не только для метрик: на стадии 2 (закрытая бета) и позже поддержке придётся менять тарифы, блокировать пользователей и разбирать жалобы. Через админку можно читать все кабинеты, поэтому угон одной сессии раскрыл бы все данные и дал бы команды над всеми кабинетами.

Код пользователей (SH-016) ещё не написан, поэтому модель можно поменять без миграции.

## Решение

1. **Где живёт.** Отдельное приложение `apps/admin` на `admin.studhub.ru`. API `/api/admin/v1` работает в том же `apps/api`, со своей спецификацией OpenAPI и своим сгенерированным клиентом. Админ ходит к данным через функции модулей, поэтому правила домена общие.
2. **Какие данные видит сотрудник.** Все кабинеты. ПДн учеников маскирует сервер, браузер админки открытых значений не получает:
   - имя ученика → «Ученик 7F3A»;
   - телефон, Telegram, email и место встречи → последние 2 символа;
   - заметки, итог и план урока, ДЗ, цели, описания и файлы материалов скрыты: видно только наличие, длину и дату;
   - деньги, цены, статусы, даты, слоты, тариф, счётчики и технические ID открыты.

   Снять маску нельзя. Чтобы найти ученика, преподаватель копирует его ID кнопкой «Скопировать ID для поддержки».
3. **Вход.** Яндекс ID или VK ID, затем TOTP. Cookie `sh_admin_session` действует только на `admin.studhub.ru`, живёт 8 часов и не продлевается. Команды, которые что-то меняют, снова просят код TOTP.
4. **Сотрудники.** Таблица `platform_staff`: `user_id`, `role`, зашифрованный секрет TOTP, `created_at`, `disabled_at`. Роли:
   - `superadmin`: всё, включая тарифы, удаление и управление сотрудниками;
   - `support`: чтение замаскированных данных и безопасные команды.

   Роли платформы не связаны с ролями кабинета (`workspace_member.role`). Админская роль не открывает кабинеты в `/api/v1`, а владелец кабинета не попадает в админку.
5. **Аудит.** `admin_audit` пишет каждый запрос к `/api/admin/v1`, и чтение, и команды. Запись делается в той же транзакции, что и команда. У приложения в БД есть только право `INSERT`. Записи хранятся 1 год.
6. **Данные преподавателя** открыты: имя, email, провайдеры входа (без ID у провайдера), часовой пояс, тариф, дата регистрации, статус удаления. По данным преподавателей StudentsHub оператор, поддержку клиентов указываем целью в политике обработки (SH-071).
7. **MVP.** Экрана метрик в MVP нет. Задача SH-065 делает события и представления `analytics`, а метрики владелец смотрит запросами из `scripts/metrics.sql` по SSH. Экран Э-18 становится отдельным экраном в `apps/admin` (SH-088).

## Рассмотренные варианты

- **Отдельный бэкенд `apps/admin-api` с прямым доступом к БД.** Изоляция по процессу, но правила домена либо дублируются, либо обходятся. Это нарушает правило «доступ к БД только в `*/db/`». Второй сервис в деплое и мониторинге.
- **Готовая админка поверх БД (AdminJS, Directus, Appsmith).** Таблицы за день, но все ПДн видны напрямую, без правил домена и аудита. Облачные варианты запрещены 152-ФЗ, свои пришлось бы держать отдельным сервисом.
- **Раздел в `apps/web`.** Дешевле сейчас, но код админки попадает в бандл преподавателя, а сессия общая, на 90 дней.
- **Доступ только к данным преподавателя.** Проще модель угроз, но жалобу про конкретного ученика не разобрать.
- **Доступ к ученикам по разрешению преподавателя на 72 часа.** Юридически чище, но владелец выбрал полный доступ с маскировкой.
- **Полный доступ без маскировки.** Взлом одной учётки раскрывает всех учеников всех преподавателей.
- **Снятие маски с поля по причине.** Возвращает путь к открытым ПДн. Можно добавить поверх решения 2: понадобится эндпоинт раскрытия и запись в аудит.
- **Доступ к админке только из WireGuard.** Снаружи админки нет совсем, но VPN нужен на каждом устройстве. Можно добавить правилом в Caddy без изменений кода.
- **Вход как у преподавателя, но с короткой сессией.** Угон Яндекс-аккаунта основателя дал бы доступ ко всем кабинетам.
- **Флаг `is_platform_admin` вместо таблицы.** Секрет TOTP пришлось бы хранить в `user`, а с первым сотрудником модель всё равно переделывать.
- **Гибкие права по действиям.** Для одного основателя и, возможно, одного сотрудника это лишняя работа. Новая роль добавляется значением `role`.
- **Аудит только команд.** При полном доступе главный вопрос «кто смотрел кабинет» остался бы без ответа.
- **Экран метрик в `apps/web` до стадии 2.** Экран пришлось бы писать дважды, а до переноса данные всех преподавателей были бы открыты по обычной сессии.

## Последствия

- В `user` нет флага администратора. SH-016 создаёт модель без него, `platform_staff` появляется в задаче SH-084.
- На каждый эндпоинт `/api/admin/v1` нужны тест на роль и тест на запись в `admin_audit`. Правило «чужой кабинет → 404» для админки не действует: сотрудник читает все кабинеты, его границы задают роль и маскировка.
- Маскировка делается на сервере в одном месте, общем для всех админских ответов. Тест проверяет, что в ответах нет открытых ПДн.
- Сессии разделены: `sh_session` не открывает `/api/admin/v1`, `sh_admin_session` не открывает `/api/v1`.
- Фоновая задача удаления аккаунта (UC-S4) пишет факт удаления в `admin_audit` с пустым `staff_user_id`. Так же в проекте помечена система в `lesson_status_change` (`changed_by = NULL`). У `admin_audit.workspace_id` нет внешнего ключа: после удаления кабинета запись должна остаться.
- Как удалять записи старше года при праве только на `INSERT` (отдельная роль БД или партиции по месяцам), решает SH-086.
- До каркаса админки метрики доступны только владельцу и только с компьютера с SSH-ключом.
- Расширение: новые роли платформы добавляются значением `role`, VPN-доступ добавляется в Caddy, раскрытие поля по причине добавляется отдельным эндпоинтом.
