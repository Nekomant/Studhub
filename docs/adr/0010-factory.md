# ADR-0010: Фабрика задач — локальный скрипт без модели

- Статус: принято
- Дата: 2026-11-13
- Меняет `docs/process.md`: §7 и §7.1 (способ запуска задачи)

## Контекст

Сейчас запуск задачи ведёт штаб на Opus. Штаб проверяет Ready, создаёт ветку, запускает сессию и `sh-worker`, разбирает ответ. Это работа по жёстким правилам. Каждый шаг тратит контекст и запросы дорогой модели.

Фабрика делает ту же работу локальным скриптом. Владелец запускает её командой из терминала. Штаб остаётся для спецификаций и решений.

## Решение

1. **Фабрика — локальный Node-скрипт без модели.** Правила процесса выполняет код: выбор задачи, ветка, worktree, проверка спецификации, установка зависимостей, состояние. Команда: `pnpm factory` ([README.md](../../README.md#запуск-задачи-pnpm-factory)). Состояние лежит в `<git common dir>/factory/` и не попадает в рабочее дерево и коммиты.
2. **Модель работает только в трёх местах:** `sh-worker`, `sh-verifier` и code-review. Воркер и верификатор работают на Sonnet по своим агентам. Code-review работает на Sonnet по решению владельца (SH-100).
3. **Воркер запускается с правами `--permission-mode dontAsk`.** Задача получает списки разрешённых и запрещённых инструментов. Режим `bypassPermissions` не используется.
4. **Старт только по команде владельца.** `pnpm factory run` — прямая команда владельца. Хуки, расписания, циклы и автозапуск по списку Ready не строим (правило ручного старта, `docs/process.md` §7).

### Принятый риск: обход запретов

Список инструментов ограничивает команды по префиксу. Разрешённые широкие правила позволяют обойти запреты:

- `pnpm` разрешает `pnpm exec git push`;
- подкоманды `git` с любыми флагами разрешают `git branch -D`;
- `git diff`, `git log` и `git show` пишут в файл через `--output`;
- `node scripts/…` запускает любой скрипт папки;
- Edit и Write не ограничены по пути.

Список защищает от случайного действия, а не от намеренного обхода. Владелец принимает этот риск. Смягчают его три факта: воркер работает в своём worktree, ветку на `origin` пушит только фабрика, а PR сливает владелец после проверок CI.

## Рассмотренные варианты

- **Управляющая сессия на Haiku.** Каждый её ход — запрос к API и около 10 тыс. токенов контекста, а правила жёсткие. Код выполняет их дешевле и без ошибок интерпретации. Отклонено.
- **Режим `bypassPermissions` для воркера.** Воркер получил бы все инструменты без ограничений, в том числе `git push` и `git branch -D`. Отклонено: даже неполный список снижает риск случайного действия.
- **Автозапуск по списку Ready.** Владелец теряет контроль над расходами и порядком задач. Отклонено правилом ручного старта.
- **Состояние в `backlog/` или рабочем дереве.** Состояние попало бы в коммиты и в конфликты слияния. Отклонено: файлы лежат в `<git common dir>/factory/`.

## Последствия

- Задачи SH-094–SH-098 добавляют в фабрику запуск воркера, проверки, PR и просмотр состояния. Схему состояния и список этапов они берут из `scripts/lib/factory-state.mjs`.
- Штаб с `sh-worker` остаётся запасным способом выполнить задачу.
- Фабрика видит только Ready из `origin/main`. Ready, поставленный локально без коммита, остаётся путём штаба.
- Ветку фабрика называет транслитерацией названия задачи (`sh-NNN-<slug>`), а штаб — коротким английским именем.
