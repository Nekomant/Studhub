# Требования к новому процессу исполнения задач

Статус: черновик. Собран из обсуждения с владельцем. Заменяет текущий процесс из `docs/process.md` после согласования. Каждый этап ниже потом прорабатывается отдельно.

Принцип: всё, что идёт по чёткой схеме или с простым ветвлением, делает скрипт. Модель нужна только там, где нужно суждение или диалог с владельцем. Цель — экономия токенов.

## 1. Режимы CI

1. PR идёт в лёгкий режим, только если все изменённые файлы лежат в `docs/` (кроме `docs/process.md`) или в файлах карточек Backlog. Любой другой файл отправляет PR в полный режим (белый список).
2. Режим определяет CI по списку изменённых файлов. Автор PR его не выбирает.
3. Лёгкий режим запускает быстрые проверки: `spec:check` для изменённых карточек в Ready, формат карточек и допустимые переходы статусов, разбор документов через `scripts/doc.mjs`. Тесты, сборка образа и деплой не запускаются.
4. Обязательная проверка защиты `main` не блокирует лёгкий PR: для пропущенных проверок есть job-заглушка с тем же именем.
5. Деплой на prod запускается только при изменении продуктового кода. Правило определения то же, что для лёгкого режима. Сейчас [ci.yml](../.github/workflows/ci.yml) запускает `deploy` на любой push в `main`, это нужно изменить.
6. Тесты в `tools/tests/`, которые сейчас читают `docs/` (`docs/process.md`, `docs/technical-design.md`, `docs/adr/0010-factory.md`), переписываются вместе с новым процессом и перестают читать `docs/`, кроме `docs/process.md`. После этого любая правка `docs/` кроме `process.md` не может сломать тесты, и белый список лёгкого режима остаётся простым.

## 2. Роли

7. Фабрика — скрипт (`pnpm factory`). Он делает всю механику, которая идёт по схеме: поиск задач, проверки Ready и актуальности, ветку, worktree, права, проверки DoD, push, PR, слияние, уборку, состояние. Модель нужна там, где нужен диалог или суждение.
7a. Корневая сессия (модель, основная папка) принимает команду владельца (`/ready SH-NNN` или другую), запускает скрипт и по его результату одним вызовом `start_session` открывает подсессию с брифом. Дальше корневая сессия в процессе не участвует.
7b. В подсессии работает воркер: он её основной агент, а не субагент. Он не делает проверок готовности, пишет тесты и код по спецификации и сообщает статус фабрике (корневой сессии): «закончил», «остановился с вопросом», «остановился из-за прав», число замечаний. Дальше решает фабрика: позвать владельца, запустить ревьюера, снова запустить воркера, создать PR, запушить, слить. `start_session` не умеет задавать агента и список разрешений. Права задачи поэтому записывает скрипт в настройки worktree до старта подсессии, а `permission_mode` подсессии не выше режима корневой.
7d. Ревьюер запускается отдельным процессом, который запускает скрипт фабрики: `claude -p --agent sh-reviewer --model opus` в режиме только чтения. Ревьюер не может писать файлы: он печатает ответ в stdout в заданном формате, первая строка — вердикт («блокирует: N» или «чисто»). Скрипт проверяет формат и сам сохраняет замечания в файл. Скрипт сам разбирает вердикт, считает круги и решает: вернуть воркеру или создать PR. Воркеру передаётся только указатель на файл с замечаниями, корневая модель получает одну строку.
7d1. Команды фабрики: `factory ready` (выбор задачи, Ready, актуальность, ветка, права, бриф; запускает корень), `factory next` (одна команда, сама выбирает шаг по состоянию: проверки DoD, проверяющий тестов при необходимости, ревьюер, круги, push, PR, CI; вызывает воркер, ответ получает в тот же вызов, первая строка — действие), `factory merge` (после добра владельца: Merged и слияние; запускает корень), `factory status` (текущий этап из файла состояния).
7e. Фабрика показывает в корневой сессии текущий этап задачи короткой фразой при каждом переходе: «Воркер закончил, ждём ревьюера», «Ревьюер выдал замечания, воркер исправляет» и так далее. Фразу этапа печатает `factory next`, а воркер отправляет её в корневую сессию коротким сообщением вместе со своими вопросами. Если воркер закончил ход без вызова `factory next`, приложение будит корень, и он проверяет `factory status`.
7c. Запасной вариант, если открытие подсессии или вызов агентов в ней не работают: эти обязанности берёт на себя фабрика (фоновый `claude -p`, как сейчас, ответы через `pnpm factory answer`).
8. Воркер пишет код и тесты по спецификации. Он не меняет статусы, не проверяет готовность, не делает push, PR и слияние.
9. Ревьюер — один отдельный агент на модели Opus (сильнее воркера). Он только читает: файлы, поиск, `git diff`, `node scripts/task.mjs`. Результаты скриптов проверок ему передаёт фабрика. Ничего не меняет и не запускает. Один проход, две оси: баги и нарушения жёстких правил кода, расхождение с критериями приёмки.
9a. Замечания ревьюера делятся на два уровня. «Блокирует»: баг, нарушение жёсткого правила кода или расхождение с критерием приёмки; на каждое он указывает нарушенное правило или критерий, и воркер обязан исправить такое до PR. «Замечание»: всё остальное; воркер правит то, что в рамках задачи, остальное идёт в список замечаний и техдолг. «Вопрос владельцу»: ревьюеру нужно решение владельца (например, две трактовки критерия); не блокирует, идёт в список замечаний. Фабрика показывает только общее число замечаний, а воркер выделяет вопросы в своём списке.
9b. Жёсткие правила кода хранятся в скилле `sh-code-rules`, который подключают воркер и ревьюер через поле `skills:`. Из `CLAUDE.md` правила удаляются, остаётся ссылка. Скилл короткий: только правила, подробности в ТД §1 и §13.

## 3. Старт задачи

10. Владелец открывает сессию в корне и просит взять задачу, например через `/ready`.
11. Фабрика находит задачи в Ready. Если их несколько, спрашивает, какую брать. Одновременно в работе одна задача.
12. Фабрика проверяет Definition of Ready.
13. Фабрика проверяет актуальность спецификации скриптом по git: менялись ли после её Ready документы и файлы, перечисленные в задаче, и закрыты ли зависимости. При находках спрашивает владельца. Для этого в карточке нужны списки документов и затрагиваемых файлов.
14. Фабрика создаёт ветку и worktree и открывает подсессию с воркером.

## 4. Воркер

15. Задача, дошедшая до воркера, считается готовой. Воркер берёт спецификацию и реализует её.
16. Воркер может создавать локальные коммиты в своей ветке.
17. Если спецификация противоречит коду или нужно решение, воркер останавливается, пишет вопрос в своей подсессии и сообщает фабрике сигнал «остановился». Молча подгонять нельзя.
18. Владелец отвечает воркеру в его подсессии. Списки вопросов и замечаний не пересылаются между сессиями.
19. Права воркера: белый список. Базовый набор плюс поле «права» в карточке задачи. Запрещены push, `gh`, смена статусов, доступ вне worktree.
20. Если прав не хватило, воркер не ищет обход. Он останавливается, подробности пишет в своей подсессии, а в корневую сессию отправляет короткий текст с причиной. Право добавляется в карточку или базовый набор только по решению владельца.
21. Порядок тестов: красный коммит с тестами по критериям (`[SH-NNN AC-n]`), затем реализация.

## 5. Проверки и ревью

22. Всё, что можно проверить скриптом (тесты, линт, типы, метки критериев, красный коммит, правки тестов после него), проверяет скрипт.
23. Агент-проверяющий тестов вызывается только если скрипт нашёл правки тестов после красного коммита.
24. После проверок DoD фабрика запускает ревьюера. Замечания каждого этапа возвращаются воркеру.
25. Воркер правит замечания, которые в рамках задачи. Границу задают файлы и критерии из плана задачи. Остальное остаётся в списке замечаний.
26. Автоматических кругов «ревьюер → воркер» не больше двух. После этого фабрика создаёт PR с оставшимися замечаниями.

## 6. PR и закрытие

27. Когда критичных замечаний нет, фабрика сама создаёт PR, без подтверждения владельца.
28. После зелёного CI фабрика сообщает одной строкой: «PR готов, замечаний: N», со ссылками на PR и подсессию. Число замечаний воркер передаёт через файл состояния, текст остаётся в его подсессии.
29. Владелец смотрит замечания и PR. Если всё устраивает, он даёт добро, и фабрика сливает squash.
30. Если не устраивает, владелец разбирается с воркером в его подсессии. После правок фабрика проходит полный круг заново: проверки DoD, ревьюер, обновление PR, новый CI.
31. Уведомления: строка в корневую сессию и системное уведомление macOS.

31a. Сразу после слияния кода фабрика убирает за задачей: удаляет ветку и worktree, архивирует подсессию воркера, подтягивает `main`. Done на это не влияет. Если деплой провалился, исправление идёт новой задачей.

## 7. Статусы и Done

32. В карточке остаются статусы: черновик, Ready, Merged, Done. Промежуточные статусы In Progress и Review не хранятся.
33. Merged попадает в `main` вместе с кодом, последним коммитом ветки.
34. Done проставляет последний шаг job `deploy` после успешной выкладки: он находит в Merged все задачи, чьи SHA слияния являются предками выложенного коммита (`git merge-base --is-ancestor`), и открывает лёгкий PR с Done. PR сливается автоматически.
35. SHA задачи берётся из `main` по заголовку squash-коммита: `git log origin/main --grep='^SH-NNN:' --format=%H`.
35a. Версия сборки в `/healthz` не добавляется: `deploy.sh` запускает `up -d` с явным тегом SHA, и при сбое job красный.
36. При провале деплоя откат автоматически не делается. Задача остаётся в Merged, владелец получает сообщение и решает: откат тем же `deploy.sh` на предыдущий тег или исправление новой задачей.

## 8. Техдолг

37. Замечания, которые не исправлены в задаче, хранятся в одном файле `docs/tech-debt.md`. `pnpm remarks` читает его. Поля: источник (задача, дата, кто заметил), что не так и где, что привело и в каком контексте, что учесть при исправлении, на что может повлиять, статус.
38. Запись добавляет воркер в том же PR, где замечание появилось. Исправленное замечание удаляется из файла в PR, который его исправляет. Причина или способ — в описании PR.
39. Одна задача в работе одновременно, поэтому конфликтов в общем файле нет.
39a. При внедрении неисправленные замечания из заметок существующих карточек переносятся в `docs/tech-debt.md` разовым скриптом с источником «SH-NNN». Записи без структуры разбираются вручную. После переноса `pnpm remarks` читает только новый файл.

## 9. Состояние фабрики

40. Минимальный файл состояния вне git (в `.gitignore`): идентификатор сессии воркера, номер круга ревью, число замечаний, сигнал воркера. Шаг процесса вычисляется из git и GitHub.
41. Если файла нет, фабрика создаёт его сама. Это записано в документации.

## Внедрение

42. Процесс внедряется одним большим изменением в одной ветке, а не по этапам. Старый и новый процессы не живут вместе.
43. Риски одного большого PR: объём, изменение `ci.yml` и деплоя на prod, переписывание `docs/process.md` и `CLAUDE.md`. Внутри ветки изменения разбиваются на коммиты по темам, чтобы PR можно было читать по частям.

## Открытые вопросы


- Какие части текущей системы остаются, какие меняются, какие удаляются. Решено: `sh-spec-critic` остаётся и сам запускает `pnpm spec:check` в начале; `pnpm close-task` заменяется уборкой фабрики после слияния (п. 31a). Не решено: `pnpm factory`, `sh-worker`, `sh-verifier`, `docs/process.md`.
- Состав базового набора прав воркера и поле «права» в карточке. За основу берётся нынешний `workerAllowed` в `scripts/factory.mjs` плюс то, чего не хватало (docker).
- Как подсессия получает ветку: `start_session` создаёт свою ветку и worktree, а ветку `sh-NNN-…` готовит скрипт. Вероятно, воркер делает `git switch`, как сейчас.
