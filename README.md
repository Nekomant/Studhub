# Studhub

Веб-приложение (PWA) для частных репетиторов: ученики, расписание, оплаты, контекст уроков, материалы.
Документы:

- [`docs/product-concept.md`](docs/product-concept.md): что и зачем делаем;
- [`docs/technical-design.md`](docs/technical-design.md): как устроено, стек и правила кода;
- [`docs/process.md`](docs/process.md): как работаем над задачами.

## Установка

Нужны Node 24 и pnpm 12. Версия Node записана в `.nvmrc`, версия pnpm записана в поле `packageManager` в `package.json`.

```bash
nvm install    # один раз: ставит Node из .nvmrc
nvm use
npm install -g pnpm@12.18.0    # или corepack, если он есть в вашей сборке Node
pnpm install
pnpm --filter @studhub/ui-tokens exec playwright install chromium
```

`pnpm install` ставит зависимости всех пакетов и git-хуки lefthook (скрипт `prepare`). Вторая команда один раз
скачивает Chromium для браузерного теста темы (`packages/ui-tokens`); без неё `pnpm verify` и `pnpm test` падают
в свежем клоне или worktree. В CI этот шаг уже есть.

## Запуск

Нужны запущенный Postgres, `pnpm db:up`, и файл `.env` (раздел «Локальное окружение» ниже).

```bash
pnpm dev    # запускает API на :3000 и SPA (Vite) на :5173; остановка Ctrl+C гасит оба процесса
```

Откройте <http://localhost:5173>. Vite проксирует `/api` и `/healthz` на API (адрес меняет `API_PROXY_TARGET`),
поэтому SPA ходит к API с того же адреса, как в продакшене. Порт SPA меняет `WEB_PORT` (тогда порт обязателен). На экране «Сегодня» заглушка показывает статус `/healthz`.
Отдельно SPA запускает `pnpm --filter @studhub/web dev`, API запускает `pnpm --filter @studhub/api dev` (перезапуск при правке файлов).

Оболочка SPA: на ширине меньше 768 px нижняя панель с пятью вкладками, от 768 px боковая панель (screens.md §3.1–3.2).
Приложение ставится как PWA: manifest и service worker (vite-plugin-pwa) кэшируют только статику сборки.
Service worker работает в собранном приложении (`pnpm --filter @studhub/web build` и `preview`), в `pnpm dev` его нет.

### Админка платформы (`apps/admin`)

Отдельное приложение для сотрудников платформы ([ADR-0009](docs/adr/0009-platform-admin.md)). Сейчас это заглушка:
страница с заголовком «Админка платформы» и пометкой «Заглушка: экраны появятся в следующих задачах». Вход, API и экраны добавят следующие задачи.

```bash
pnpm --filter @studhub/admin dev      # Vite на :5174, к API не обращается
pnpm --filter @studhub/admin build    # собирает приложение в apps/admin/dist
```

### API (сервер)

Нужны запущенный Postgres (раздел ниже) и файл `.env`.

```bash
pnpm --filter @studhub/api start    # читает .env из корня; слушает PORT (по умолчанию 3000)
curl http://localhost:3000/healthz      # {"status":"ok","db":"ok"}; 503 в формате problem+json, если БД недоступна
pnpm gen:openapi                        # пишет apps/api/openapi.json (OpenAPI 3.1 из zod-схем маршрутов)
pnpm gen:client                         # пишет типы клиента packages/client-core/src/api/schema.ts из openapi.json
```

Клиент `createApiClient(baseUrl)` из `@studhub/client-core` работает на `openapi-fetch` и этих типах. После изменения маршрутов
выполните `pnpm gen:openapi`, затем `pnpm gen:client` и закоммитьте оба файла.

Маршруты кабинета и прочие API живут под `/api/v1`. Ошибки отдаются как `application/problem+json` с полем `code`.
Логи пишутся в JSON (pino) в stdout. Поля с ПДн и секреты (имена, телефоны, email, заметки, токены, cookie, Authorization) маскируются.

### Локальное окружение: Postgres 18 и Garage (S3)

Нужен Docker с Compose v2. Compose поднимает Postgres 18 и Garage, локальный сервер с S3 API
(замена MinIO, [ADR-0008](docs/adr/0008-garage-local-s3.md)). Бакет для файлов и ключ доступа Garage создаёт сам при старте.

```bash
cp .env.example .env    # один раз: переменные окружения; значения по умолчанию подходят для разработки
pnpm db:up              # поднимает контейнеры и ждёт, пока они будут готовы
pnpm db:down            # останавливает контейнеры; данные остаются в томах
```

Данные лежат в именованных томах Docker, поэтому переживают `db:down` и перезапуск. Удалить их можно командой
`docker compose down -v`. Эта команда стирает dev-данные, запускайте её осознанно.

Адреса: Postgres `localhost:5432`, S3 API `http://localhost:3900` (регион `garage`, адресация по пути).
При создании клиента `@aws-sdk/client-s3` укажите `forcePathStyle: true` и `requestChecksumCalculation: "WHEN_REQUIRED"`,
иначе presigned PUT вернёт ошибку контрольной суммы.

Тестовая БД отдельная, её имя задаётся в `TEST_DATABASE_URL` и должно оканчиваться на `_test`:

```bash
pnpm db:reset-test      # пересоздаёт только тестовую БД; dev-БД не трогает
```

Миграции БД (Drizzle, [ADR-0002](docs/adr/0002-postgres-drizzle.md)) лежат в `apps/api/drizzle/`. Команды запускайте после `pnpm db:up`:

```bash
pnpm --filter @studhub/api db:migrate     # применяет миграции к DATABASE_URL; повторный запуск ничего не меняет
pnpm --filter @studhub/api db:check       # падает, если схема изменена без миграции
pnpm --filter @studhub/api db:generate    # генерирует миграцию по схеме модулей
pnpm --filter @studhub/api start migrate  # то же самое через приложение: так миграции запускает CD
```

Соглашения схемы БД описаны в [`apps/api/src/modules/README.md`](apps/api/src/modules/README.md).

Если порты 5432 или 3900 заняты, задайте `POSTGRES_PORT` или `S3_PORT` в `.env` и поправьте адреса в `DATABASE_URL`,
`TEST_DATABASE_URL`, `S3_ENDPOINT`.

Приложение проверяет переменные окружения при старте по схеме `apps/api/src/platform/config`. Если переменной нет
или её значение неверно, процесс печатает список проблем и завершается с кодом 1. Список переменных — в `.env.example`.

## Проверки

| Команда       | Что делает                                                                                       |
| ------------- | ------------------------------------------------------------------------------------------------ |
| `pnpm check`  | Biome проверяет формат и линт (`biome ci`), TypeScript проверяет типы во всех пакетах (`tsc -b`) |
| `pnpm test`   | Vitest запускает тесты всех проектов из `vitest.config.ts`                                       |
| `pnpm test:api` | Запускает только API-тесты (`tests/api`): приложение на тестовой БД, клиент из OpenAPI. Нужен `pnpm db:up` |
| `pnpm test:e2e` | Собирает SPA и админку и запускает Playwright (`tests/e2e`) против сборки: БД `<имя>_e2e_<случайная часть>_test` рядом с `TEST_DATABASE_URL`, API и `vite preview` на свободных портах; админка отдаётся отдельным `vite preview` на порту `E2E_ADMIN_PORT` (по умолчанию `E2E_PORT` + 1, то есть 4174). Нужны `pnpm db:up` и Chromium (`pnpm --filter @studhub/ui-tokens exec playwright install chromium`) |
| `pnpm gen:client:check` | Падает, если `packages/client-core/src/api/schema.ts` не совпадает с генерацией из `openapi.json` |
| `pnpm format` | Biome исправляет формат и порядок импортов                                                       |
| `pnpm db:check` | Падает, если схема Drizzle изменена без миграции                                               |
| `pnpm ac:check` | Падает, если у задачи в Merged или Done критерий без метки `[SH-NNN AC-n]` в тестах (`docs/process.md` §8.2) |
| `pnpm spec:check` | Проверяет спецификацию задач по шаблону и Definition of Ready (`docs/process.md` §4, §5). `pnpm spec:check SH-NNN` проверяет указанные задачи в любом статусе, без аргументов все задачи в Ready, с `--changed` Ready-задачи, изменённые относительно `origin/main` |
| `pnpm verify` | `pnpm check` и тесты с коротким выводом                                                          |

Перед коммитом и пушем запускайте `pnpm verify`. CI (`.github/workflows/ci.yml`) на каждый PR и push в `main`
запускает `pnpm check`, сборку админки (`pnpm --filter @studhub/admin build`), `pnpm db:check`, `pnpm gen:client:check`, `pnpm ac:check`, `pnpm test:api`, `pnpm test` и `pnpm test:e2e` на Postgres 18. Браузеры Playwright кэшируются по `pnpm-lock.yaml`. На PR он ещё запускает `pnpm spec:check --changed`.

Git-хуки (`lefthook.yml`):

- `pre-commit` проверяет Biome-ом файлы из коммита. Если он нашёл ошибки формата, запустите `pnpm format`.
- `commit-msg` проверяет заголовок по [Conventional Commits](https://www.conventionalcommits.org/ru/):
  `<тип>(<область>): <описание>`, типы `feat`, `fix`, `test`, `refactor`, `docs`, `chore`, `ci`, `build`
  (`docs/process.md` §9).

### Очистка локальных веток

После слияния PR GitHub удаляет ветку, а локальная копия остаётся. PR сливаются через squash, поэтому
`git branch --merged` такие ветки не находит. Их находит скрипт `scripts/git-prune.mjs`:

```bash
pnpm git:prune            # git fetch --all --prune и список веток, удалённых на GitHub; ничего не удаляет
pnpm git:prune --delete   # удаляет ветки из этого списка и печатает каждую удалённую с её SHA
```

В список не попадают `main`, ветки без upstream (их не пушили на GitHub) и ветки, открытые в любом worktree.
Ветку из worktree скрипт удалит, когда вы уберёте worktree: `git worktree remove <папка>`.
`--delete` удаляет ветку принудительно (`git branch -D`), в том числе с коммитами, которых нет на GitHub.
Если ветку удалили по ошибке, верните её по SHA из вывода скрипта: `git branch <имя> <SHA>`.

### Основная папка: `pnpm sync`

Запускайте в основной папке клона. `pnpm sync` приводит её в порядок после слияний PR:

```bash
pnpm sync            # ничего не меняет; показывает отставание от origin/main, файлы задач в backlog/, совпадающие с origin/main, и ветки, удалённые на GitHub
pnpm sync --apply    # подтягивает main перемоткой (--ff-only), сбрасывает только совпавшие файлы задач, удаляет только показанные ветки
```

Если историю нельзя перемотать до `origin/main`, скрипт слияния не делает и сообщает об этом. Другие незакоммиченные правки он не трогает.

### Запуск задачи: `pnpm factory`

Фабрика — локальный скрипт без модели ([ADR-0011](docs/adr/0011-factory-orchestrator.md)), ведёт задачу по схеме через
статусы **Backlog → Ready → Merged → Done** и подключает модель только там, где нужно суждение или диалог с владельцем.
Запуск — только по команде владельца: автозапуска нет. Запускать можно из любой папки клона.

```bash
pnpm factory ready SH-NNN    # выбор и проверка задачи (DoR, актуальность), ветка, worktree, права, бриф для подсессии
pnpm factory ready            # без номера: спрашивает, какую задачу взять
pnpm factory next             # проверки DoD, ревьюер, push, PR, ожидание CI (первая строка — действие воркеру)
pnpm factory merge            # после добра владельца: ретро, статус Merged, squash-слияние, уборка
pnpm factory status           # текущий этап задачи из файла состояния
```

Скрипт делает `git fetch origin` и читает задачи из `origin/main`, а не из рабочей папки. Ready, поставленный без
коммита, фабрика не видит: это путь штаба (`docs/process.md` §7, шаг 3). `factory ready` проверяет Definition of Ready
скриптом `check-spec.mjs`, сверяет файлы и документы из поля «Затрагивает» задачи с их состоянием на момент перехода
в Ready (при изменениях печатает их и не готовит задачу без подтверждения владельца), создаёт ветку `sh-NNN-<slug>`
и worktree от `origin/main`, записывает права задачи и модель воркера в настройки worktree и печатает бриф. Корневая
сессия по брифу открывает подсессию (`start_session`) в worktree задачи; воркер — её основной агент. `factory next`
одной командой проходит проверки DoD, ревьюера, круги, push, PR и CI; `factory merge` после добра владельца коммитит
статус Merged, сливает squash, удаляет ветку и worktree, подтягивает `main` и архивирует подсессию. Статус Done ставит
шаг `deploy` (скрипт `scripts/mark-done.mjs`) после успешной выкладки.

В приложении задачу стартует скилл `/ready` (`.claude/skills/ready/SKILL.md`), его набирает только владелец.
`/ready SH-NNN` вызывает `pnpm factory ready SH-NNN`, открывает подсессию в worktree задачи с брифом и показывает фразы
этапа; по добру владельца скилл вызывает `pnpm factory merge` и архивирует подсессию после слияния.

Запасной вариант с фоновым воркером (`dsh headless`), если открытие подсессии или вызов агентов в ней не работают:

```bash
pnpm factory run             # печатает кандидатов, спрашивает номер (или y/n при одном кандидате), готовит выбранную задачу
pnpm factory run SH-NNN      # пропускает выбор и готовит указанную задачу
pnpm factory run --foreground           # то же, но воркер идёт в этом окне, без фонового процесса
pnpm factory run SH-NNN --foreground    # указанная задача, воркер в этом окне
pnpm factory list                       # печатает кандидатов без вопросов, ничего не создаёт и не запускает
pnpm factory                            # сводка: задачи, их этапы и вопросы к владельцу
pnpm factory answer SH-NNN "текст"      # ответ на этап «стоп»: воркер продолжает работу через --resume
pnpm factory answer SH-NNN "текст" --foreground   # то же, воркер идёт в этом окне
pnpm factory continue SH-NNN            # повтор воркера после этапа «ошибка»
pnpm factory continue SH-NNN --foreground         # то же, воркер идёт в этом окне
pnpm factory drop SH-NNN                # снять задачу с фабрики (спрашивает y/n)
```

Кандидат — задача в Ready, у которой все зависимости в Done, нет ветки `sh-NNN-*` (локальной и на `origin`),
нет worktree на такой ветке и нет записи фабрики. Задачи Ready с зависимостью не в Done печатаются отдельным блоком «Ждут зависимость».
Статус зависимости скрипт определяет и по задачам из `backlog/archive/tasks` и `backlog/completed`; кандидатами бывают только задачи из `backlog/tasks`.
Пустой ввод, `n`, не число или номер вне списка: «Ничего не запущено», код 0, ничего не создано.

`pnpm factory list` делает `git fetch origin`, отбирает кандидатов так же, как `run`, и печатает без вопросов.
Строка кандидата: `SH-NNN`, приоритет («не указан», если его нет) и название через табуляцию, по возрастанию номера.
Затем, если есть задачи, ждущие зависимость, идёт блок `Ждут зависимость:` с такими же строками. Кандидатов нет: первая строка «Задач в Ready нет».
У `list` нет аргументов и флагов: лишнее даёт код 2. Коды выхода `list`: 0 — список напечатан, 1 — сбой `git fetch origin` или нет `origin/main`, 2 — неверный вызов.

Для выбранной задачи в запасном режиме скрипт:

1. создаёт ветку `sh-NNN-<slug>` и worktree `<основная папка>/.claude/worktrees/sh-NNN-<slug>` от `origin/main`;
2. запускает `node scripts/check-spec.mjs SH-NNN --root <worktree>`;
3. ставит зависимости в worktree: `pnpm install --frozen-lockfile`;
4. создаёт запись состояния с этапом «подготовлена» и печатает ID, ветку и путь к worktree;
5. запускает воркера: `dsh headless --agent sh-worker` в worktree задачи с правами `--permission-mode dontAsk` и бюджетом. Списки разрешённых и запрещённых инструментов лежат в `scripts/lib/factory-tools.mjs`.

Без `--foreground` воркера ведёт фоновый процесс. Команда печатает ID, ветку и путь к журналу и сразу завершается с кодом 0.
Запись получает этап «в работе», `pid` и время старта процесса. С `--foreground` команда ждёт ответа воркера в этом окне.
Фабрика ведёт не больше двух задач с живым фоновым процессом: третий запуск печатает причину и выходит с кодом 1.
`pnpm factory run SH-NNN` для записи на этапе «подготовлена» сразу запускает воркера: `git fetch`, `check-spec` и `pnpm install` повторно не идут. Для записи на другом этапе скрипт печатает причину и выходит с кодом 1.
Права воркера ограничены (`scripts/lib/factory-tools.mjs`): базовый набор плюс поле «Права» карточки. Запрещены `git push`, `gh`, `curl`, `rm -rf`, смена статусов и доступ вне worktree. Режим `dontAsk` отклоняет составную команду целиком, если часть не подходит под правила. Остаточные риски широких правил перечислены в ADR-0010, раздел «Принятый риск: обход запретов».
Переменные окружения воркер берёт из `.env` основной папки и worktree, только из списка `ALLOWED` в `scripts/lib/local-env.mjs`.
Журнал задачи: `<git common dir>/factory/SH-NNN/log.txt`.

#### Остановки, ответ владельца и сводка

Когда задача переходит на этап, который ждёт владельца (список `STAGES_WAIT_OWNER` в `scripts/lib/factory-state.mjs`), процесс, сменивший этап, показывает уведомление macOS с заголовком «Фабрика».
Текст: `SH-NNN · <этап> · <деталь>`, не длиннее 100 символов, лишнее отрезается без многоточия. Деталь — первая строка ответа для «стоп», `reason` для остальных этапов.
Текст идёт в `osascript` отдельным аргументом: кавычки и `\` в ответе модели команду не ломают. Если `osascript` нет или он завершился с ошибкой, текст попадает в журнал задачи, фабрика работает дальше.

- `pnpm factory answer SH-NNN "текст"` работает только на этапе «стоп». Фабрика ставит этап «в работе» и продолжает воркера ответом владельца. Текст уходит одним аргументом процесса, без оболочки и без изменений, и записывается в журнал.
- `pnpm factory continue SH-NNN` работает на этапе «ошибка»: продолжает сессию или делает новый старт в том же worktree, без `check-spec`.
- `answer` и `continue` подчиняются лимиту двух живых процессов. На другом этапе, без записи или при исчерпанном лимите они печатают причину, выходят с кодом 1 и воркера не запускают. `--foreground` работает как в `run`.
- `pnpm factory drop SH-NNN` снимает задачу с фабрики. При живом процессе задачи он сразу выходит с кодом 1. Иначе спрашивает `y/n`. После `y` он убирает запись из `state.json`, удаляет чистый worktree и локальную ветку, если её нет на `origin` и worktree удалён, и печатает SHA ветки. Грязный worktree и ветку на `origin` он не трогает и называет. Журнал задачи остаётся.
- `pnpm factory` без аргументов печатает сводку не длиннее 30 строк. Сначала идут задачи, которые ждут владельца, затем остальные; внутри групп от старых к новым. Строка задачи: `SH-NNN  <этап>  <время>  <стоимость>`. Последняя строка: «Ждут тебя: N». Задача, которая не помещается, не печатается; вместо неё строка «…ещё K задач». Пустое состояние: «Фабрика пуста».
- Задача на этапе, где работает процесс (например, «в работе»), а процесс не жив: сводка, `run`, `answer` и `continue` ставят этап «ошибка» с причиной «процесс завершился без ответа» и показывают уведомление.

Slug — транслитерация названия: первые три слова через дефис, не длиннее 30 символов; если в названии нет букв и цифр, slug равен `task`.
Если проверка спецификации, установка или блокировка состояния закончились ошибкой, скрипт удаляет созданные ветку и worktree и выходит с кодом 1.
Для `pnpm factory run SH-NNN` с задачей, которая не кандидат, скрипт печатает причину, ничего не создаёт и выходит с кодом 1.
Коды выхода: 0 — воркер запущен или запуск отменён, 1 — ничего не запущено, 2 — неверный вызов.

Состояние лежит в `<git common dir>/factory/`: `state.json`, блокировка `state.lock/` и папка `SH-NNN/` с журналом `log.txt`.
Папка общая для основной папки и всех worktree клона, в рабочее дерево и коммиты она не попадает.
Основную папку скрипт берёт из первой записи `git worktree list --porcelain`.

### Границы слоёв

Правила границ из ТД §13 проверяет Biome (`noRestrictedImports` в `overrides` файла `biome.json`):

1. `apps/web`, `packages/client-core` и `tests/*` не импортируют `apps/api`.
2. `*/domain/*` не импортирует Hono, Drizzle, драйверы БД, `db/` и `http/`.
3. Модули сервера общаются только через `index.ts`: импорт `modules/<модуль>/{domain,db,http}/` из другого модуля
   запрещён. Biome видит только текст пути импорта, поэтому свой модуль он узнаёт по форме `../domain/`,
   `../../db/` и так далее, до четырёх `../`. Из более глубоких папок такой импорт тоже получит ошибку.
   Модуль состоит из `index.ts`, `domain/`, `db/` и `http/` (ТД §2.4). Других файлов и папок в корне модуля
   правило не видит, поэтому их не заводим. Импорты из `platform/` разрешены.
4. Drizzle, драйверы БД и `platform/db/` импортируются только в `*/db/`.

Biome заменяет опции правила в каждом подходящем блоке `overrides`, а не складывает их. Поэтому каждый блок
перечисляет все запреты для своих файлов. Правила проверяет тест `tools/tests/boundaries.test.ts` на фикстурах
`tools/boundary-fixtures/`: файл `*.bad.ts` нарушает одно правило, файл `*.ok.ts` не нарушает ни одного. Если меняете
правила, добавьте фикстуру.
