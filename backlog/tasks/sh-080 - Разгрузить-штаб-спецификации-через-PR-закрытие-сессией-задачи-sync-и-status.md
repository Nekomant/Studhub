## Что нужно сделать
1. Спецификации через PR. Описать в `docs/process.md` §3.1, §5 и §7: штаб пишет и правит задачи в своей ветке `specs-…` в worktree, а не в основной папке, и открывает PR «Спецификации: SH-…» на одну или несколько задач. Задачи, которые штаб предлагает к работе, в PR уже в статусе Ready. Владелец читает их в PR, просит правки комментариями и сливает. Слияние PR спецификаций означает согласование: статус Ready попадает в `main` вместе со слиянием. Задачи, которые владелец не согласовал, штаб убирает из PR или возвращает в Backlog.
2. Старт задачи от `main`. Убрать из `docs/process.md` §7 и §7.1 и из скилла `sh-task` перенос файла задачи из основной папки и коммит Ready: сессия задачи стартует от `main`, где задача уже в Ready.
3. Закрытие цикла сессией задачи. Описать в `docs/process.md` §7.1 и в скилле `sh-task`: о слиянии владелец пишет сессии задачи. Она проверяет, что PR слит и в `main` у задачи статус Done, переводит свой worktree на `origin/main` без ветки, удаляет свою локальную ветку и архивирует себя (`archive_session` с `self`; приложение спрашивает подтверждение). Если PR не слит или статус в `main` не Done, сессия ничего не удаляет и сообщает владельцу.
4. Команда `pnpm sync` для основной папки: подтягивает `main` только перемоткой (`--ff-only`), показывает незакоммиченные файлы задач, совпадающие с `main`, и локальные ветки, удалённые на GitHub (как `pnpm git:prune`). Без флага ничего не меняет; с флагом сбрасывает только файлы задач, совпадающие с `main`, и удаляет только показанные ветки. Чужие незакоммиченные правки не трогает никогда.
5. Команда `pnpm status`: задачи в Ready, In Progress и Review, открытые PR с состоянием CI (`gh pr list`), worktree и их ветки. Вывод короткий, для штаба и владельца.
6. Шаблон брифа рабочей сессии в `docs/process.md` §7.1: ID задачи, ссылка на §7.1 и особенности задачи в нескольких строках. Процесс в брифе не пересказывать.
7. Описать команды в README и `CLAUDE.md`.
8. Написать тесты по критериям.

## Зачем
В сессии штаба 2026-11-12 большая часть работы была текучкой, а не спецификациями. Владелец ставил Ready правкой в основной папке, правка лежала незакоммиченной, сессия копировала файл к себе, а после слияния штаб сбрасывал устаревшие копии, подтягивал `main` и чистил ветки. Так было с SH-077, SH-078 и SH-009. Ещё штаб передавал сессиям «готов слить» и «влил» и проверял слияние. Брифы пересказывали процесс на 2–3 тыс. знаков.

Автоархивация сессий в приложении не подходит: это настройка аккаунта, она действует на все проекты, и владелец её выключил. Поэтому сессия задачи архивирует себя сама после проверки слияния.

После этой задачи у штаба остаются спецификации, решения по объёму и приёмка: работа, ради которой ему нужна сильная модель.

## Контекст
- `docs/process.md` §3.1 (статусы), §5 (Definition of Ready), §7 и §7.1 (жизненный цикл, `sh-worker`), §9 (Git).
- `.claude/skills/sh-task/SKILL.md`: чеклисты старта и финиша.
- `scripts/git-prune.mjs`: поиск веток, удалённых на GitHub, и пропуск веток в worktree.
- Защита `main`: ruleset, слияние только через PR при зелёной проверке `checks`, ветка PR должна быть актуальной относительно `main`.

## Не входит

- Агент-верификатор: SH-079.
- Автоматическое слияние и действия GitHub после слияния.
- Перенос задач, которые уже лежат незакоммиченными в основной папке (SH-079 и чужая правка SH-076): их владелец и штаб разбирают отдельно.

## Контракт
API и БД не меняются. Новые команды `pnpm sync` и `pnpm status` в `package.json`.
