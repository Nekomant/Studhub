## Что нужно сделать
1. CI ([ci.yml](.github/workflows/ci.yml)): добавить job определения режима по списку изменённых файлов. Лёгкий режим — все файлы в `docs/` (кроме `docs/process.md`) или в `backlog/`. В лёгком режиме запускать только `spec:check --changed`, проверку формата карточек и разбор документов `scripts/doc.mjs`; job-ы тестов, `image` и `deploy` пропускать, обязательную проверку `checks` закрывать заглушкой с тем же именем. `deploy` на push в `main` запускать только при изменении файлов полного режима.

4. Шаг Done в job `deploy`: после успешной выкладки скрипт `scripts/mark-done.mjs` находит задачи в Merged, чьи squash-коммиты (`^SH-NNN:` в `origin/main`) являются предками выложенного SHA, и открывает лёгкий PR «Done: SH-…» с автослиянием. При красном `deploy` статусы не меняются, отката нет.
5. Фабрика (`scripts/factory.mjs`, `scripts/lib/`): команды `ready`, `next`, `merge`, `status` по `docs/pipeline-requirements.md` §2–§9. Повторно использовать подготовку ветки и worktree, файл состояния и уведомления macOS из текущей фабрики. Файл состояния — вне git, фабрика создаёт его сама.
6. `factory ready`: выбор задачи, Definition of Ready (`check-spec.mjs`), проверка актуальности по git (изменения документов и файлов из задачи после её перехода в Ready, зависимости в Done), ветка и worktree, запись прав задачи в настройки worktree, бриф для подсессии.
7. Поля «Права» и «Затрагивает» в шаблоне задачи (`docs/process.md` §4) и их проверка в `spec:check`. «Права» принимает известные значения, каждое раскрывается в правила разрешений поверх базового набора (нынешний `workerAllowed` плюс права SH-105). «Затрагивает» перечисляет файлы и документы, которые меняет задача; `factory ready` использует его для проверки актуальности.
8. `factory next`: проверки DoD скриптами (тесты, линт, типы, `ac:check`, красный коммит, правки тестов после него), проверяющий тестов `sh-verifier` только при правках тестов после красного коммита, ревьюер, счёт кругов (не больше двух автоматических), push, `gh pr create`, ожидание CI. Первая строка вывода — действие для воркера, вторая — фраза этапа.
9. `factory merge`: после добра владельца коммит статуса Merged в ветке, push, ожидание CI, squash-слияние, удаление ветки и worktree, `git pull` в основной папке. Заменяет `pnpm close-task`; `close-task.mjs` удалить.

Разрешённые инструменты: Read, Grep, Glob, Bash для `git diff`, `git log`, `git show`, `cat`, `ls`, `head`, `tail`, `wc`; запрещены Edit, Write, `git commit`, `git push`, `git branch -d`/`-D`, `gh`.

## Зачем
Текущий процесс смешивает роли: воркер сам проверяет готовность, ведёт статусы и разговаривает с фабрикой блоками текста, а владелец отвечает через команды терминала. PR с документами и карточками гоняют весь CI и даже деплой. Done ставится до того, как код выложен на сервер. Каждый шаг, который мог сделать скрипт, тратит токены модели.

## Контекст

- Процесс: `docs/process.md` §3–§10, ADR-0010 (фабрика).
- Деплой: ТД §12, `infra/deploy.sh`, ADR-0007.
- Задачи: SH-105 (базовый набор прав воркера, делается первой).
- Поглощает архивированные задачи SH-095, SH-096, SH-097, SH-099, SH-100, SH-101 (ступени старой фабрики): их логика перенесена в эту задачу.

## Не входит
- Параллельная работа над несколькими задачами: одна задача в работе одновременно.
- Версия сборки в `/healthz`.
- Стенд на PR и smoke-проверки по критериям задачи на prod.
- Автоматический откат деплоя.
- Перевод `sh-spec-critic` на скрипты сверх первого шага `spec:check`.

## Контракт
Нет изменений API и БД. Меняются: статусы Backlog, формат карточки (поля «Права» и «Затрагивает»), команды `pnpm factory`, удаляется `pnpm close-task`, новый файл `docs/tech-debt.md`, новые агент и скилл.
