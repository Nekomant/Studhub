## Что нужно сделать
1. Написать тесты по критериям до реализации: `tools/tests/factory.test.ts`. Фикстуры собрать как в `tools/tests/close-task.test.ts`: bare-репозиторий вместо GitHub, основная папка, файлы задач в `backlog/tasks`. `claude` и `gh` подменить скриптами в `PATH`: они пишут аргументы и `cwd` в журнал и печатают заготовленный JSON. `backlog` в фикстуре — настоящий CLI или подмена, на выбор исполнителя. Настоящую модель тесты не запускают. ID задач в фикстурах из диапазона SH-9xx.
2. Записать ADR `docs/adr/0010-factory.md`:
   - фабрика — локальный Node-скрипт без модели, правила процесса в нём выполняет код;
   - модель работает только в `sh-worker`, `sh-verifier` и code-review, все на Sonnet;
   - управляющая сессия на Haiku отклонена: каждый её ход — запрос к API и около 10 тыс. токенов контекста, а правила жёсткие;
   - воркер работает в режиме `--permission-mode dontAsk` со списком разрешённых и запрещённых инструментов; `bypassPermissions` не используется. Принятый риск: список ограничивает команды по префиксу, поэтому разрешённые широкие правила (`pnpm`, `node scripts/…`, подкоманды `git` с любыми флагами, Edit и Write без ограничения пути) позволяют обойти запреты, например `pnpm exec git push` или `git branch -D`. Список ограничивает случайные действия, а не намеренный обход; ветку пушит только фабрика;
   - старт только командой владельца, автозапуска нет.
3. Написать `scripts/factory.mjs` и команду `factory` в `package.json`. Скрипт работает из любой папки клона: основную папку берёт из первой записи `git worktree list --porcelain`, как `scripts/close-task.mjs`.
4. Состояние. Хранить в `<git common dir>/factory/` (`git rev-parse --git-common-dir`): файл `state.json` и папка `SH-NNN/` с журналом `log.txt` (каждая смена этапа — строка с временем, старым и новым этапом) и JSON-ответами `claude` по порядку (`001-worker.json`, …). В рабочее дерево и коммиты состояние не попадает. Схему задать в `scripts/lib/factory-state.mjs`, её используют SH-094–SH-097:
   - запись задачи: `id`, `title`, `branch`, `worktree`, `stage`, `stage_changed_at`, `reason`, `session_id`, `session_ready`, `pid`, `pid_started_at`, `cost_usd`, `rounds`, `rounds_total`, `denials`, `verify_summary`, `review_count`, `pr_url`, `updated_at`;
   - `session_ready` становится `true` после первого ответа `claude` с этим `session_id`: только тогда сессию можно продолжать через `--resume`. `denials` — отказы последнего запуска `claude`, каждый раз перезаписываются. `pid_started_at` — время старта процесса из `ps -o lstart= -p <pid>`;
   - `cost_usd` — сумма `total_cost_usd` всех запусков `claude` по задаче (воркер, верификатор, ревью); `pid` — процесс фабрики, который ведёт задачу в фоне, вместе с временем его старта;
   - этапы: «в работе», «готово», «стоп», «ошибка», «проверки», «нужен владелец», «нужен штаб», «ошибка проверок», «готово к PR», «ошибка PR», «PR», «Done, ждёт слияния». Этапы, на которых работает процесс, — «в работе» и «проверки» (SH-095 добавит к ним «готово»); остальные ждут владельца. Оба списка — константы модуля.
   - запись `state.json` атомарная: во временный файл и `rename`, под блокировкой `state.lock` (создание каталога `mkdir`, повтор до 5 секунд). Так два фоновых процесса не теряют изменения друг друга;
   - в `log.txt` фабрика пишет строкой с временем каждый запуск команды `claude`, `git`, `gh` и каждую смену этапа со старым этапом, новым и `reason`.
5. `pnpm factory run` без аргумента:
   1. делает `git fetch origin` и читает задачи из `origin/main` (`git show`), а не из рабочей папки. Ready, поставленный локально без коммита (§7, шаг 3.1), фабрика не видит: это путь штаба;
   2. кандидаты: статус Ready, все зависимости в Done, нет локальной ветки `sh-NNN-*`, ветки `origin/sh-NNN-*`, worktree на такой ветке и записи в `state.json`. Ветка на `origin` значит, что задачу начали в другом клоне или сессии;
   3. печатает кандидатов пронумерованным списком: ID, название, приоритет, число критериев. Задачи Ready с зависимостью не в Done печатает отдельным блоком «Ждут зависимость» без номера;
   4. несколько кандидатов: спрашивает номер. Один кандидат: показывает его и спрашивает `y/n`. Пустой ввод, `n`, не число или номер вне списка: «Ничего не запущено», код 0, ветки, worktree и записи нет. Кандидатов нет: «Задач в Ready нет», код 0.
6. `pnpm factory run SH-NNN` пропускает выбор. Если задача не кандидат, печатает причину (не Ready, зависимость не в Done, есть ветка, есть запись фабрики), код 1, ничего не создаёт.
7. Для выбранной задачи фабрика:
   1. создаёт ветку `sh-NNN-<slug>` и worktree `<основная папка>/.claude/worktrees/sh-NNN-<slug>` от `origin/main` (`git worktree add -b`);
   2. slug строит из названия: русские буквы по таблице а-a б-b в-v г-g д-d е-e ё-e ж-zh з-z и-i й-y к-k л-l м-m н-n о-o п-p р-r с-s т-t у-u ф-f х-kh ц-ts ч-ch ш-sh щ-shch ы-y э-e ю-yu я-ya; ъ и ь отбрасываются; латиница и цифры как есть, остальные знаки — разделители слов; первые три слова через дефис в нижнем регистре; пока длина slug (без префикса `sh-NNN-`) больше 30 и слов больше одного, последнее слово отбрасывается; одно слово длиннее 30 обрезается до 30 букв; без дефиса в конце; если в названии нет ни буквы, ни цифры, slug — `task`. Примеры: «Фабрика: запуск задачи командой pnpm factory run» → `fabrika-zapusk-zadachi`, «Объём подъёма» → `obem-podema`;
   3. запускает `node scripts/check-spec.mjs SH-NNN --root <worktree>`. Код не 0: печатает вывод скрипта, удаляет worktree и ветку, код 1;
   4. ставит зависимости в worktree: `pnpm install --frozen-lockfile`. Код не 0: печатает последние 20 строк вывода, удаляет worktree и ветку, код 1;
   5. создаёт запись в `state.json` с этапом «в работе», запускает фоновый процесс фабрики, печатает ID, ветку и путь к журналу и сразу завершается с кодом 0. Фоновый процесс запускает воркер и разбирает ответ. Флаг `--foreground` делает то же в текущем процессе и ждёт ответа: для тестов и отладки.
8. Команда воркера: `claude -p "Новый старт SH-NNN. Ветка: sh-NNN-<slug>." --agent sh-worker --session-id <uuid> --name "Фабрика SH-NNN" --output-format json --permission-mode dontAsk --allowedTools <правила> --disallowedTools <правила> --max-budget-usd <лимит>`, `cwd` — worktree задачи. Каждый список правил — один аргумент, правила через запятую.
9. Списки и лимит в `scripts/lib/factory-tools.mjs`:
   - правила записываются в формате Claude Code: имя инструмента или `Bash(<префикс команды>:*)`. Модуль экспортирует функцию `matchesRule(rule, command)`: команда подходит к правилу, если начинается с префикса, за которым конец строки или пробел (`Bash(ls:*)` подходит к `ls -la`, но не к `lsof`); тесты проверяют списки через неё;
   - разрешено: Read, Edit, Write, Grep, Glob; Bash для `pnpm`, `node scripts/…`, `backlog task …`, `ls`, `cat`, `mkdir`, `docker compose` и подкоманд `git add`, `commit`, `status`, `log`, `diff`, `show`, `switch`, `branch`, `rev-parse`;
   - запрещено (`--disallowedTools`): `git push`, `gh`, `curl`, `rm -rf`;
   - лимит бюджета одного запуска воркера — константа; значение исполнитель выбирает и записывает в заметки.
10. Не больше двух задач с живым фоновым процессом. Процесс жив, если pid есть и время его старта совпадает с `pid_started_at`. При двух живых `run` отказывает с кодом 1 и называет их задачи.
11. Разбор ответа без модели: JSON `claude` — `result`, `session_id`, `total_cost_usd`, `permission_denials`. Первая непустая строка `result` после обрезки пробелов: `ГОТОВО SH-NNN` с ID этой задачи даёт этап «готово», `СТОП SH-NNN: …` — этап «стоп». Другой текст, ID другой задачи, ненулевой код, невалидный JSON, `is_error: true` или нет поля `result` (например, превышен бюджет) дают этап «ошибка» с причиной в `reason`. Если JSON валиден, `total_cost_usd` прибавляется к `cost_usd` и отказы пишутся в `denials` при любом коде; `session_ready` становится `true`, если `session_id` ответа совпал с записанным.

    - `tools/tests/docs-dedup.test.ts`: добавить `pnpm factory` в список проверяемых команд, тест зелёный;
    - `docs/process.md` §7 и §7.1: фабрика — основной способ выполнять задачу, сессия штаба с `sh-worker` — запасной. Правило ручного старта уточнить: `pnpm factory run` — прямая команда владельца; запрещён старт без команды (хуки, расписания, циклы, автозапуск по списку Ready). Фабрика стартует из любой папки клона и видит только Ready из `origin/main`; ветку называет slug транслитерацией, а не английским именем;
    - `.claude/agents/sh-worker.md`: воркер запускает сессия задачи или фабрика;
    - `CLAUDE.md`: блоки про штаб и `sh-worker`.

## Зачем
Сейчас запуск задачи ведёт штаб на Opus: проверяет Ready, создаёт ветку, запускает сессию и `sh-worker`, разбирает ответ. Это работа по жёстким правилам, и каждый шаг тратит контекст и запросы Opus. Фабрика делает то же локальным скриптом без модели. Владелец запускает её одной командой из терминала, а штаб остаётся для спецификаций и решений.
