## Что нужно сделать
1. Написать тесты по критериям до реализации в `tools/tests/factory.test.ts` с фикстурами SH-093 и SH-094. Подставной `claude` различает вызовы по аргументам (`--agent sh-worker`, `--agent sh-verifier`, `/code-review`) и печатает заготовленный ответ для каждого. `pnpm verify` в фикстуре подменить скриптом с заданным кодом выхода.
2. Этап «готово» перенести в список этапов, где работает процесс (`scripts/lib/factory-state.mjs`). Когда воркер вернул `ГОТОВО`, фоновый процесс ставит этап «проверки» и выполняет по порядку. Следующий шаг идёт, только если предыдущий чистый:
   1. `pnpm verify` в worktree. Код не 0 — замечание с выводом команды;
   2. верификатор: `claude -p "Проверь SH-NNN" --agent sh-verifier --output-format json --permission-mode dontAsk --allowedTools <список верификатора> --max-budget-usd <лимит>`, `cwd` — worktree;
   3. ревью: `claude -p "/code-review high" --model sonnet --append-system-prompt "Последней строкой выведи: ЗАМЕЧАНИЙ: <число>" --output-format json --permission-mode dontAsk --allowedTools <список ревью> --disallowedTools <запреты ревью> --max-budget-usd <лимит>`, `cwd` — worktree.
3. Разбор отчёта верификатора без модели:
   - строка `ПРОВЕРКА SH-NNN` обязательна;
   - вердикт — первые слова сразу после `AC-n:`: «подтверждён», «сомнительно» или «не подтверждён». Слова в пояснении после `—` не учитываются;
   - «не подтверждён» проверяется раньше «подтверждён»: второе слово входит в первое;
   - замечание: хотя бы один «не подтверждён» или строка «Нарушения правила…» после снятия кавычек и точки не равна «нет»;
   - «сомнительно» не замечание: фабрика пишет такие строки в журнал, а в заметки они попадают с итогом (шаг 8). Владелец увидит их в PR (SH-097);
   - число строк `AC-n:` должно равняться числу критериев с автоматическим уровнем (Юнит, API, E2E) в плане тестов задачи (`parseTestPlan`, `levelNeedsLabel` из `scripts/lib/backlog-task.mjs`), а строка «Не смог проверить» после снятия кавычек и точки — «нет». Иначе этап «ошибка проверок».
4. Разбор ответа ревью: берётся последняя строка вида `ЗАМЕЧАНИЙ: <число>`. Число больше 0 — замечание с полным текстом ревью.
5. Замечания фабрика передаёт воркеру дословно: `claude -p "Продолжение SH-NNN. Замечания: <источник>: <текст>"`, где источник — `pnpm verify`, `sh-verifier` или `code-review`, --resume <session_id> --agent sh-worker` с флагами SH-093, этап «в работе». Каждая передача увеличивает `rounds` и `rounds_total` на 1. Новое `ГОТОВО` запускает проверки заново с `pnpm verify`. `СТОП` ведёт на этап «стоп», как в SH-094.
6. Круги. Круг — одна передача замечаний воркеру. `rounds` считает круги с последнего `continue`, `rounds_total` — за всю жизнь задачи. Если замечание есть, а `rounds` уже 2, фабрика ставит этап «нужен штаб» и замечание воркеру не передаёт. Замечания всех кругов пишутся в журнал задачи.
7. Ошибки проверок. Этап «ошибка проверок» с причиной в `reason`, если: у верификатора или ревью ненулевой код, невалидный JSON, `is_error: true` или `subtype`, начинающийся с `error` (так `claude` сообщает о превышении бюджета); в отчёте верификатора нет строки `ПРОВЕРКА SH-NNN`; в ответе ревью нет строки `ЗАМЕЧАНИЙ: <число>`; в worktree есть незакоммиченные файлы после `ГОТОВО` (проверка до `pnpm verify`); процесс фабрики умер на этапе «проверки» (сводка, `run`, `answer` и `continue` ставят этот этап вместо «ошибка» из SH-094).
8. Чистые проверки: фабрика пишет одну строку итога в заметки — `--append-notes "Проверка тестов: AC-1 подтверждён; AC-2 сомнительно: <фраза>; …"` — и сразу коммитит файл задачи (`chore(backlog): SH-NNN итог проверок`), чтобы worktree остался чистым. В состояние пишет `verify_summary` (последняя строка вывода `pnpm verify`) и `review_count` (число из `ЗАМЕЧАНИЙ:`, то есть 0). Этап «готово к PR». До SH-097 это этап, который ждёт владельца; SH-097 продолжает с него.
9. Стоимость каждого запуска верификатора и ревью прибавляется к `cost_usd`. Лимиты бюджета верификатора и ревью — константы в `scripts/lib/factory-tools.mjs`, значения исполнитель записывает в заметки.

Bash верификатора ограничивает его хук `verifier-bash-guard.mjs` (команды чтения и запуск тестов), поэтому он может вызвать всё из своего описания: `node scripts/task.mjs`, `git diff`, `git log`, `git show`, `git branch`, `grep`, `cat`, `head`, `tail`, `wc`, `find`, `pnpm test`, `pnpm exec vitest run`;

Сопоставление — через `matchesRule` из SH-093.

## Зачем
После `ГОТОВО` сессия задачи на Opus сейчас запускает верификатор и `/code-review` и гоняет замечания воркеру. Решения тут принимают верификатор и ревью, а остальное — порядок шагов и разбор строк отчёта. Фабрика делает это скриптом, модель тратится только на верификатор и ревью на Sonnet. Лимит в два круга не даёт фабрике тратить запросы на задачу, которая не сходится: её получает штаб.
