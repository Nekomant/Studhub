## Что нужно сделать
1. Написать тесты по критериям до реализации в `tools/tests/factory.test.ts` с фикстурами SH-093. Эта задача меняет поведение SH-093 в двух местах: после подготовки `run` идёт дальше этапа «подготовлена», а `run SH-NNN` на записи с этапом «подготовлена» не отказывает. SH-093 не задаёт поведение `run SH-NNN` для этапа «подготовлена»: его вводит эта задача. Тестам SH-093 после этой задачи нужна заглушка `claude` в `PATH`, их проверки не меняются. Разбор и запись ответа тестируются функциями `parseWorkerReply`, `applyWorkerReply` и `saveReply` из `scripts/factory.mjs` напрямую. `claude` подменить скриптом в `PATH`: он пишет аргументы и `cwd` в журнал и печатает заготовленный JSON. Настоящую модель тесты не запускают.
2. Запуск после подготовки. Когда SH-093 подготовила задачу, `pnpm factory run` не останавливается на этапе «подготовлена»: ставит «в работе», запускает фоновый процесс фабрики внутренней подкомандой `node scripts/factory.mjs _worker SH-NNN` (не флаг и не описывается в README), записывает его pid и время старта, печатает ID, ветку и путь к журналу и сразу завершается с кодом 0. Фоновый процесс запускает воркер и разбирает ответ. `pnpm factory run SH-NNN` для задачи на этапе «подготовлена» запускает воркер без повторной подготовки. При запуске фабрика пишет в запись `session_id` — тот же uuid, что передаёт в `--session-id`. В режиме `--foreground` pid и время старта — текущего процесса. Флаг `--foreground` делает то же в текущем процессе и ждёт ответа: для тестов и отладки.
3. Команда воркера: `claude -p "Новый старт SH-NNN. Ветка: sh-NNN-<slug>." --agent sh-worker --session-id <uuid> --name "Фабрика SH-NNN" --output-format json --permission-mode dontAsk --allowedTools <правила> --disallowedTools <правила> --max-budget-usd <лимит>`, `cwd` — worktree задачи. Каждый список правил — один аргумент, правила через запятую.
4. Списки и лимит в `scripts/lib/factory-tools.mjs`:
   - экспорты: `WORKER_ALLOWED`, `WORKER_DISALLOWED`, `WORKER_BUDGET_USD`, `matchesRule`; `matchesRule` для правила-имени инструмента (`Read`) сравнивает имя, для `Bash(…)` — команду;
   - правила записываются в формате Claude Code: имя инструмента или `Bash(<префикс команды>:*)`. Модуль экспортирует функцию `matchesRule(rule, command)`: команда подходит к правилу, если начинается с префикса, за которым конец строки или пробел (`Bash(ls:*)` подходит к `ls -la`, но не к `lsof`); тесты проверяют списки через неё;
   - разрешено: Read, Edit, Write, Grep, Glob; Bash для `pnpm`, `node scripts/task.mjs`, `node scripts/doc.mjs`, `node scripts/check-ac-coverage.mjs`, `node scripts/check-spec.mjs`, `node scripts/verify.mjs`, `backlog task`, `ls`, `cat`, `head`, `tail`, `grep`, `wc`, `mkdir`, `docker compose` и подкоманд `git add`, `commit`, `status`, `log`, `diff`, `show`, `switch`, `branch`, `rev-parse`, `fetch`, `merge-base` (их советует `sh-worker.md`, в том числе в конвейерах `| tail -n 40`);
   - запрещено (`--disallowedTools`): `git push`, `gh`, `curl`, `rm -rf`;
   - лимит бюджета одного запуска воркера — константа; значение исполнитель выбирает и записывает в заметки.
5. Не больше двух задач с живым фоновым процессом. Процесс жив, если pid есть и время его старта совпадает с `pid_started_at`. При двух живых `run` отказывает с кодом 1 и называет их задачи.
6. Разбор ответа без модели — функция `parseWorkerReply({ stdout, code, taskId, sessionId })` возвращает `{ stage, reason, cost, denials, sessionReady }`; `applyWorkerReply(id, reply)` пишет результат в запись: ставит этап, прибавляет `cost` к `cost_usd`, заменяет `denials`, ставит `session_ready` true, если `sessionReady` (обратно в false не сбрасывает), обнуляет `pid`; `saveReply(id, role, stdout)` пишет ответ в папку задачи. `reason`: для «стоп» — первая строка ответа, для «готово» — пусто, для «ошибка» — `код <N>`, `невалидный JSON`, `is_error`, `ошибка claude: <subtype>` (если `subtype` начинается с `error`), `нет result`, `чужой ID`, `неизвестный ответ` или `claude не запустился: <ошибка>`. Первая строка совпадает с `ГОТОВО SH-NNN` целиком или начинается с `СТОП SH-NNN:`. Каждый ответ, в том числе невалидный stdout как есть, пишется в папку задачи файлом `NNN-worker.json`, где NNN — максимальный номер среди всех файлов ответов задачи плюс один (`saveReply` с ролью `worker`; SH-099 и SH-100 используют роли `verifier` и `review`). `denials` хранится массивом объектов `permission_denials` как есть, без поля — пустой массив. JSON `claude` — `result`, `session_id`, `total_cost_usd`, `permission_denials`. Первая непустая строка `result` после обрезки пробелов: `ГОТОВО SH-NNN` с ID этой задачи даёт этап «готово», `СТОП SH-NNN: …` — этап «стоп». Другой текст, ID другой задачи, ненулевой код, невалидный JSON, `is_error: true` или нет поля `result` (например, превышен бюджет) дают этап «ошибка» с причиной в `reason`. Если JSON валиден, `total_cost_usd` прибавляется к `cost_usd` и отказы пишутся в `denials` при любом коде; `session_ready` становится `true`, если `session_id` ответа совпал с записанным.
7. Обновить документы (команды с флагами только в `README.md`, правило SH-081):
    - `docs/process.md` §7.1: как фабрика запускает воркер, режим `dontAsk`, лимит двух процессов;
    - `.claude/agents/sh-worker.md`: воркер запускает сессия задачи или фабрика;
    - `CLAUDE.md`: блок про `sh-worker`;
    - `README.md`: фоновый запуск, `--foreground`, где лежит журнал.
