## Description

## Что нужно сделать
1. Создать workflow GitHub Actions на PR и push в `main`. Он запускает проверки, которые есть в проекте сейчас: установка с кэшем pnpm, `pnpm check` (Biome и `tsc`), `pnpm test` (Vitest) на сервисе `postgres:18` с `TEST_DATABASE_URL`, `pnpm db:check`.
2. Написать `scripts/check-ac-coverage`: берёт задачи в статусах Review и Done из Backlog.md (`backlog task list --json` или файлы `backlog/tasks`), ищет метки `[SH-NNN AC-n]` в тестах и печатает непокрытые критерии. Покрыть скрипт юнит-тестом на фикстурах и подключить в workflow.
3. Создать `.github/pull_request_template.md` по `docs/process.md` §9–10.
4. На тестовом PR убедиться, что каждый вид сломанной проверки делает CI красным, и записать время прогона.
5. Владелец: включить защиту `main` так, чтобы слияние было возможно только при зелёном CI (имя обязательной проверки сообщит рабочая сессия).

## Зачем
Процесс «спецификация → тесты → код» держится на автоматических проверках: PR с красными проверками или непокрытыми критериями не должен сливаться. Сейчас CI нет, поэтому DoD «CI зелёный» нельзя выполнить: у SH-005, SH-077 и SH-078 этот пункт остался открытым. Задачу сузили до проверок, которые уже есть (решение владельца, 2026-11-12), чтобы не ждать каркас SPA и Dockerfile. Остальные проверки ТД §12 добавят задачи, которые создают то, что проверяется: SH-006, SH-008 и SH-011.

Оценка: 4 ч

Ждёт владельца: как check-ac-coverage обходится с критериями, которые по плану тестов проверяются вручную или ревью (сейчас без меток SH-075 AC-1..6, SH-077 AC-3, 9, 10, SH-078 AC-1, 2, 5; у самой SH-009 AC-1, 3, 4).

Решение владельца (2026-11-12): вариант А. check-ac-coverage читает таблицу «План тестов»: уровни «Ручная», «Ревью», «Скрипт» без метки, диапазоны «1–5»; метка нужна для Юнит, Unit, API, E2E; без таблицы — для всех; пропуски печатаются. AC-2 и process §8.2 поправлены в этом PR, старые задачи не трогаем. Корневой алиас pnpm db:check.

Решение: имя обязательной проверки для защиты main — checks (job checks в .github/workflows/ci.yml). Шаги после установки идут с if: !cancelled() и успешной установкой, чтобы в одном прогоне были видны все упавшие проверки.
Решение: корневые скрипты pnpm db:check (алиас на @studhub/api) и pnpm ac:check.
Решение: check-ac-coverage ищет метки только в *.test.* и *.spec.*, пропускает node_modules, backlog, скрытые папки и папки *fixtures. Если у критерия есть метка, он покрыт при любом уровне в плане; пропущенными печатаются только ручные критерии без метки. Неизвестный уровень (например, «Фикстуры») требует метку.
Проверка AC-2: pnpm exec vitest run tools/tests/check-ac-coverage.test.ts — 9 тестов зелёные; pnpm ac:check на текущем репозитории — код 0, пропущены SH-075 AC-1–6, SH-077 AC-3, 9, 10, SH-078 AC-1, 2, 5.
Проверка AC-3: .github/pull_request_template.md содержит задачу, что сделано, как проверено, изменения документов и чек-лист §10 дословно.
AC-1 и AC-4 требуют прогона на GitHub (пуш делает сессия задачи): тестовые PR со сломанными Biome, tsc, тестом и миграцией и замер времени прогона.
Факт: 1,5 ч (без прогона CI на GitHub).

Ждёт владельца: после первого зелёного прогона включить защиту main с обязательной проверкой checks (шаг 5, DoD 8).

Проверка AC-1 на GitHub (PR 15 зелёный, временный PR 17 закрыт, ветка удалена): Biome упал на неотформатированном файле (шаг «Biome и tsc»); tsc упал с TS2322 при зелёном Biome (шаг «Biome и tsc»); тест expect(1).toBe(2) уронил шаг «Vitest на Postgres 18»; таблица без миграции уронила шаг «Миграции соответствуют схеме». Шаги после упавшего выполняются, в каждом прогоне видны все ошибки.
