## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## Что нужно сделать
1. Владелец: создать бакет у второго провайдера в РФ (например, Yandex Object Storage) и Telegram-бота для алертов.
2. Настроить wal-g для Postgres: архивация WAL, ежедневный полный бэкап, шифрование libsodium, хранение 30 дней.
3. Написать скрипт проверки восстановления: поднять копию во временном контейнере, сверить число строк ключевых таблиц; поставить в cron раз в неделю.
4. Написать cron-скрипт алертов в Telegram: бэкапу больше 26 ч, проверка восстановления упала, диск заполнен больше чем на 80%, мало памяти. Без ПДн.
5. Подключить UptimeRobot к `/healthz`.
6. Один раз выполнить восстановление на момент времени и описать шаги в `infra/README.md`.

## Зачем
Потеря данных преподавателя — главный риск доверия (ТД §16). Бэкап без проверки восстановления бэкапом не считается.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Оценка: 8 ч

Владелец создал бакет и бота. Провайдер VK Cloud Object Storage, endpoint https://hb.ru-msk.vkcloud-storage.ru, регион ru-msk, бакет bucket-studhub (Icebox, без версионирования). Ключи и токен бота владелец кладёт в .env на prod сам.

Ждёт владельца: проверки на prod по infra/README.md шаг 12 (AC-1…AC-5). Код и тесты готовы: backup.test.ts 40 тестов, pnpm verify зелёный. wal-g локально не запускался (доступ запрещён), поэтому формат backup-list и выбор бэкапа для PITR в restore-fetch.sh не проверены.
Решение: имена переменных WALG_* и AWS_* (как задал владелец), бинарник wal-g v3.0.9 ставит backup/install.sh в /srv/studhub/bin, cron на хосте, хранение через delete retain FULL 30.
Замечание 1: ключи бакета (AWS_*, WALG_*) попадают в контейнер app через env_file: .env.
Замечание 2: UptimeRobot на бесплатном тарифе проверяет раз в 5 минут, не в 1.
Замечание 3: ТД §12 называл Yandex Object Storage примером, выбран VK Cloud; ТД поправлен.

Решение владельца: замечание 1 принято. Ключи AWS_*, WALG_*, TELEGRAM_* лежат в /srv/studhub/.env.backup (права 600), шаблон infra/.env.backup.example. Файл читают контейнер postgres (env_file) и скрипты backup. Контейнер app его не читает.
Решение владельца: замечание 2 принято. Интервал UptimeRobot 5 минут. Критерий AC-4 и ТД §12 поправлены.
Порядок на prod: шаги 2-3 (scp и install.sh) выполняет сессия по SSH, ключ WALG_LIBSODIUM_KEY создаёт владелец, остальные шаги владелец присылает выводами.

Решение владельца: Telegram закрыт с VPS, алерты идут через Cloudflare Worker (infra/telegram-proxy/worker.js). В .env.backup добавлены TELEGRAM_API_URL (адрес Worker) и TELEGRAM_PROXY_SECRET (общий секрет, заголовок X-Proxy-Secret). Критерии AC-3 и AC-4 не менялись.
Находка на prod: в образе postgres нет корневых сертификатов, wal-g не проходил TLS и висел минутами. Исправлено: compose монтирует /etc/ssl/certs/ca-certificates.crt с хоста, SSL_CERT_FILE задан, временные контейнеры restore-check получают тот же файл, archive_command обёрнут в timeout 180, WALG_S3_MAX_RETRIES=5.
