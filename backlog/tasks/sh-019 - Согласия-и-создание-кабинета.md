## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## Что нужно сделать
1. Добавить в конфигурацию текущие версии документов `pd_processing` и `terms` со ссылками.
2. До реализации написать API-тесты по критериям, включая смену версии документа и сбой внутри транзакции.
3. Добавить в `GET /me` поле `consentsRequired`.
4. Реализовать `POST /me/consents`: запись согласий и при первом согласии — создание кабинета и членства `owner` в одной транзакции.
5. Закрыть ресурсы кабинета ответом 403 `consent_required`, пока согласия не даны.

## Зачем
152-ФЗ требует отдельного согласия на обработку ПДн (ТД §9). Кабинет создаётся в момент согласия, чтобы у пользователя без согласия не было данных.

## Контекст
- Сценарии: UC-01 (шаги 7–9), UC-02 (2б).
- Экраны: Э-02.
- Правила: ТД §4.2 (`consent`, `workspace`, `workspace_member`), §9 «Документы».

## Не входит
- Базовые теги навыков — задача этапа 5 «Прогресс» (с заполнением для существующих кабинетов).
- Базовые шаблоны сообщений — задача этапа 7 «Шаблоны сообщений».
- Экран согласий — задача «Экраны входа и согласий».

## Контракт
- `GET /api/v1/me` → `+ consentsRequired: [{ kind, version, url }]`.
- `POST /api/v1/me/consents` `{ consents: [{ kind, version }], timezone }` → 200 `{ workspaceId }`.
- Ошибки: 403 `consent_required`, 422 `consent_incomplete`, 422 `consent_version_outdated`.

## План тестов
| AC | Уровень | Тест |
|---|---|---|
| 1 | API | новый пользователь: consentsRequired и 403 на ресурс кабинета |
| 2 | API | записи consent; один документ из двух → 422 |
| 3 | API | кабинет, членство, значения по умолчанию; повторный вызов |
| 4 | API | смена версии в конфиге → снова требуется; кабинет не дублируется |
| 5 | API | сбой внутри транзакции (тестовая инъекция) → нет частичных данных |

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Пока пользователь не принял текущие версии обоих документов, `GET /me` возвращает их в `consentsRequired`, а запросы к ресурсам кабинета → 403 `code: consent_required`
- [ ] #2 `POST /me/consents` записывает по одной записи `consent` на документ с версией, временем, IP и user-agent; при первом входе принять только один документ из двух нельзя (422 `consent_incomplete`)
- [ ] #3 Первое согласие в одной транзакции создаёт кабинет (`plan = beta`, часовой пояс из запроса, валюта RUB, политика 24 ч / 100% / 100%) и членство `owner` с `ical_anonymized = true`; повторный вызов второй кабинет не создаёт
- [ ] #4 После смены версии документа в конфигурации пользователь снова получает этот документ в `consentsRequired`; повторное согласие записывает `consent` и не создаёт кабинет
- [ ] #5 Ошибка внутри транзакции не оставляет частичных данных: нет кабинета без членства и записей согласия
