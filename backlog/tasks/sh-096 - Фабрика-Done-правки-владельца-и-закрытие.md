Фабрика всегда вызывает `node <основная папка>/scripts/close-task.mjs`.
2. `pnpm factory done SH-NNN` — владелец посмотрел PR и готов слить:
   1. работает только на этапе «PR». Иначе — причина, код 1;
   2. читает PR: `gh pr view <pr_url> --json state,statusCheckRollup`. Если PR уже слит, печатает «PR уже слит: запусти pnpm factory close SH-NNN», код 1;
   3. checks оценивает, как `ciState` в `scripts/status.mjs`: допустимы `SUCCESS`, `SKIPPED` и `NEUTRAL`. Если checks нет, есть незавершённые или упавшие, печатает их имена или «checks нет», код 1, ничего не коммитит;
   4. номера пунктов DoD «CI зелёный», «Пройдено ревью» и «PR слит» ищет по началу текста пункта в `backlog/config.yml` (`definition_of_done`). Пункт не найден: печатает его текст, код 1;

   6. этап «Done, ждёт слияния», вывод «Можно сливать. CI после этого коммита запустится заново, close-task проверит его итог».
3. `pnpm factory fix SH-NNN "текст"` — владелец просит правки по PR:
   1. работает на этапах «PR» и «Done, ждёт слияния». Иначе — причина, код 1, `claude` не вызывается. Лимит процессов и `--foreground` — как в SH-094; лимит проверяется до любых коммитов;
   2. на этапе «Done, ждёт слияния» сначала: `-s Review --uncheck-dod` для тех же трёх пунктов, коммит `chore(backlog): SH-NNN снова на ревью`, push;
   3. обнуляет `rounds`, ставит этап «в работе» и передаёт текст воркеру дословно: `claude -p "Продолжение SH-NNN. Замечания владельца: <текст>" --resume <session_id> --agent sh-worker` с флагами SH-098;
   4. дальше всё идёт обычным путём: `ГОТОВО` → проверки SH-095 → шаги PR SH-097. Так как `pr_url` есть и статус Review, SH-097 не создаёт новый PR: коммитит файл задачи, если он изменён, пушит ветку и возвращает этап «PR». `СТОП` и ошибки обрабатываются, как в SH-094 и SH-095.
4. `pnpm factory close SH-NNN` — после слияния PR владельцем:
   1. запускает `node <основная папка>/scripts/close-task.mjs SH-NNN --apply` с `cwd` — основная папка (из другой папки `close-task` не уберёт worktree задачи, SH-091) и печатает его вывод. Запись в `state.json` может отсутствовать или быть на любом этапе: `close-task` сам проверяет слияние, Done в `origin/main` и checks;
   2. при последней строке `ЗАКРЫТЬ СЕССИЮ: да` и наличии записи переносит её в `<git common dir>/factory/done.jsonl` одной строкой JSON: `id`, `title`, `cost_usd`, `rounds_total`, `closed_at` (дата `YYYY-MM-DD`). Запись из `state.json` удаляется, журнал задачи остаётся;
   3. при `ЗАКРЫТЬ СЕССИЮ: нет (…)` или коде не 0 состояние не меняется, код выхода `close` равен коду `close-task`.
5. Сбои `backlog task edit`, `git commit` и `git push` в `done` и `fix`: фабрика печатает команду и первую непустую строку её stderr, завершается кодом 1, этап не меняет. Повтор команды безопасен: коммит делается, только если файл задачи изменён и не закоммичен.

## Зачем
После PR сессия задачи на Opus ждёт «готов слить», ставит Done, возвращает Review при правках, а штаб потом запускает `pnpm close-task`. Это шаги по жёстким правилам. Фабрика делает их командами владельца без модели, кроме самих правок воркера. Файл `done.jsonl` показывает, сколько стоила каждая задача.

## Контекст
- Процесс: `docs/process.md` §3.1, §6, §7 (шаг 9, порядок правок после Done), §7.1 (шаги 6–7, `pnpm close-task`).
- Скрипты: `scripts/close-task.mjs` (SH-091), `scripts/status.mjs` (`ciState`), `backlog/config.yml` (`definition_of_done`).
- Фабрика: SH-093 (состояние, этапы), SH-094 (сводка, уведомления, лимит процессов), SH-095 (проверки), SH-097 (PR, `pr_url`).
- UC и экраны: нет, задача про процесс разработки.

## Не входит
- Слияние PR: его делает только владелец.
- Своя проверка слияния и удаление веток: это делает `pnpm close-task`, фабрика его вызывает.
- Чтение комментариев PR с GitHub: текст правок владелец передаёт в `fix` сам.
- Ожидание CI после коммита Done: итог проверяет `close-task`.

## Контракт
API и БД не меняются. Новое: команды `pnpm factory done`, `fix`, `close`, файл `<git common dir>/factory/done.jsonl`.
