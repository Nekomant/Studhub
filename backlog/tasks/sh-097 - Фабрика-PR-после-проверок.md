## Что нужно сделать
1. Написать тесты по критериям до реализации в `tools/tests/factory.test.ts` с фикстурами SH-093–SH-100. Подставной `gh` пишет аргументы и содержимое `--body-file` в журнал. Этапы проверяются по журналу смен этапов `log.txt` (SH-093): так тесты SH-095–SH-100 про «готово к PR» остаются верными, хотя после этой задачи процесс идёт дальше.
2. Этап «готово к PR» перенести в список этапов, где работает процесс (`scripts/lib/factory-state.mjs`): с него фоновый процесс сразу выполняет шаги PR, уведомления на нём нет. Если процесс умер на «готово к PR», сводка, `run`, `answer` и `continue` ставят «ошибка PR» с `reason` «процесс завершился без ответа» (вместо «ошибка» из SH-094).
3. Шаги PR (все команды с `cwd` — worktree задачи):
   1. проверка отметок. Критерий считается «Ревью», если все его строки в плане тестов имеют уровень «Ревью» (`normalizeLevel` из `scripts/lib/backlog-task.mjs`); критерий без строки в плане проверяется как остальные. Критерии «Ревью» не проверяются: владелец проверяет их по PR и отмечает командой `backlog task edit SH-NNN --check-ac N` в worktree задачи до `pnpm factory done`; `done` (SH-096) коммитит файл задачи целиком вместе с этими отметками. Критерии «Юнит», «API», «E2E» и «Скрипт» отмечает воркер с доказательством. Если неотмечен любой критерий, кроме «Ревью», этап «нужен владелец», `reason` — `не отмечены: AC-3, AC-5`, уведомление, дальше фабрика не идёт. Обычно это «Ручная»: владелец проверяет и отмечает её той же командой;
   2. если статус задачи не Review, `backlog task edit SH-NNN -s Review`. Затем, если файл задачи изменён и не закоммичен (статус, отметки владельца), `git add <файл задачи>` и коммит `chore(backlog): SH-NNN на ревью`. Условие коммита — изменённый файл, а не значение статуса: так повтор после сбоя `git commit` не оставит статус незакоммиченным;
   3. `git push -u origin sh-NNN-…`;
   4. если `pr_url` есть, фабрика больше ничего не вызывает: пуш обновил PR. Если `pr_url` пуст, она ищет открытый PR ветки (`gh pr list --head <ветка> --state open --json url`); нашла — пишет ссылку в `pr_url`. Не нашла — `gh label create factory --force`, затем `gh pr create --title "SH-NNN: <название>" --label factory --body-file <git common dir>/factory/SH-NNN/pr-body.md`. В этой задаче тело — две строки: «Собрано фабрикой» и `SH-NNN: <название>`. SH-101 строит полное тело по шаблону, и оно тоже начинается строкой «Собрано фабрикой» и содержит `SH-NNN: <название>`, последнюю непустую строку вывода (ссылку `https://…`) пишет в `pr_url`;
   5. этап «PR», уведомление.
4. Сбой `backlog task edit`, `git add`, `git commit`, `git push`, `gh label create`, `gh pr list`, `gh pr create` или записи `pr-body.md` ставит этап «ошибка PR» с `reason` вида `<команда>: <первая непустая строка stderr, иначе stdout>`, где команда — её первые слова без аргументов (`backlog task edit`, `git add`, `git commit`, `git push`, `gh label create`, `gh pr list`, `gh pr create`), например `git push: fatal: …`; для записи файла — `запись pr-body.md: <ошибка>`, шлёт уведомление. Уже сделанные шаги при повторе не дублируются: коммит — только если файл задачи изменён, PR — только если `pr_url` пуст и открытого PR ветки нет.
5. `pnpm factory continue SH-NNN` на этапах «нужен владелец» и «ошибка PR» ставит этап «готово к PR» с новым pid и повторяет шаги PR с шага 3.1, без проверок SH-095, SH-099 и SH-100. Лимит процессов и `--foreground` — как в SH-094.
6. Сводка `pnpm factory`: для этапа «PR» под строкой задачи — строка `PR: <pr_url>`.
7. Обновить документы (команды с флагами только в `README.md`):
   - `docs/process.md` §7 (шаг 8) и §7.1 (шаг 5): при работе через фабрику коммит Review, пуш и PR делает фабрика; метка `factory` и первая строка тела «Собрано фабрикой» отличают её PR; критерии «Ревью» владелец проверяет по PR и отмечает командой `backlog` в worktree задачи, а `pnpm factory done` (SH-096) коммитит их вместе с Done;
   - таблица статусов §3.1: Review может поставить фабрика, до открытия PR и до CI, как уже допускает §7, шаг 8. Это изменение решения: в PR фабрики критерии «Ревью» при статусе Review ещё не отмечены, их отмечает владелец; строку Review поправить;
   - `CLAUDE.md`: строку «Ревью, пуш, PR и статусы Review и Done делает сессия» и правило 3 о порядке «PR → статус Review» дополнить фабрикой;
   - `README.md`: этапы «нужен владелец», «ошибка PR», «PR» и `continue` для них.

## Зачем
После проверок сессия задачи на Opus сейчас ставит Review, пушит ветку и открывает PR. Это детерминированные шаги. Фабрика делает их без модели и отдаёт владельцу PR с меткой `factory`. Описание PR по шаблону добавляет SH-101.

## Контекст
- Процесс: `docs/process.md` §3.1 (таблица статусов), §7 (шаг 8), §7.1 (шаг 5).
- Фабрика: SH-093 (состояние, `pr_url`, этапы, журнал), SH-094 (уведомления, сводка, `continue`), SH-095, SH-099, SH-100 (проверки, «готово к PR»).
- Разбор плана тестов: `scripts/lib/backlog-task.mjs` (`parseTestPlan`).
- UC и экраны: нет, задача про процесс разработки.

## Не входит
- Тело PR по шаблону: SH-101.
- Статус Done, правки по ревью владельца, закрытие: SH-096.
- Слияние PR: его делает только владелец. Проверка итога CI: `pnpm factory done` в SH-096.

## Контракт
API и БД не меняются. Новое: шаги PR в `scripts/factory.mjs`, этапы «нужен владелец», «ошибка PR», «PR», файл `pr-body.md` в папке задачи, метка PR `factory`, поле `pr_url`.

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 Если на этапе «готово к PR» неотмечен критерий, у которого не все строки плана тестов имеют уровень «Ревью» (в том числе критерий без строки плана), фабрика ставит этап «нужен владелец» с reason «не отмечены: AC-n, …», шлёт уведомление и не делает коммит, push и вызовы gh
- [ ] #2 Неотмеченный критерий, у которого все строки плана тестов имеют уровень «Ревью», при отмеченных остальных шаги PR не останавливает
- [ ] #3 Если статус задачи не Review, фабрика ставит Review; если файл задачи изменён и не закоммичен, фабрика делает git add файла задачи и коммит chore(backlog): SH-NNN на ревью; затем пушит ветку sh-NNN-… в origin
- [ ] #4 Если pr_url пуст и gh pr list --head <ветка> не нашёл открытого PR, фабрика вызывает gh label create factory --force и gh pr create с заголовком «SH-NNN: <название>», --label factory и --body-file из папки задачи, тело которого начинается строкой «Собрано фабрикой» и содержит строку «SH-NNN: <название>», пишет в pr_url последнюю непустую строку вывода gh pr create, ставит этап «PR» и шлёт уведомление; переход на «готово к PR» уведомления не даёт
- [ ] #5 Если PR уже есть, фабрика не создаёт второй: при непустом pr_url после push не вызываются gh pr list, gh label create и gh pr create, а если pr_url пуст и gh pr list нашёл открытый PR ветки, фабрика пишет его ссылку в pr_url без gh pr create; этап «PR»
- [ ] #6 Коммит статуса делается только при изменённом файле задачи: если файл не изменён и статус уже Review, git commit не вызывается; если git commit упал после backlog task edit -s Review, то после pnpm factory continue коммит Review в ветке ровно один, а worktree чист
- [ ] #7 Сбой backlog task edit, git add, git commit, git push, gh label create, gh pr list, gh pr create или записи pr-body.md ставит этап «ошибка PR» с reason «<команда>: <первая непустая строка stderr, иначе stdout>», где команда — её первые слова без аргументов (например «git push: fatal: …»), и шлёт уведомление; сбой записи pr-body.md даёт reason «запись pr-body.md: <ошибка>»
- [ ] #8 pnpm factory continue SH-NNN на этапах «нужен владелец» и «ошибка PR» ставит этап «готово к PR» с новым pid и повторяет шаги PR, не запуская pnpm verify и claude

## Definition of Done
<!-- DOD:BEGIN -->
- [ ] #1 Каждый критерий приёмки покрыт тестом, в названии теста есть ID критерия (AC-n), все тесты зелёные
- [ ] #2 CI зелёный: Biome, tsc, Vitest, API-тесты, E2E, миграции и OpenAPI-клиент актуальны (с момента, когда эти проверки появились в CI)
- [ ] #3 Документы (use-cases, screens, technical-design, ADR) обновлены в этом же PR, если поведение или решения изменились
- [ ] #4 Новые эндпоинты покрыты тестом изоляции (чужой кабинет → 404); в логах и product_event нет ПДн; деньги только в minor units
- [ ] #5 Пройдено ревью (/code-review и просмотр диффа владельцем), замечания закрыты
- [ ] #6 PR слит в main через squash, изменения выложены в prod (после появления деплоя)
- [ ] #7 В заметках задачи записаны оценка и фактическое время, решения по ходу работы и итоговое резюме
